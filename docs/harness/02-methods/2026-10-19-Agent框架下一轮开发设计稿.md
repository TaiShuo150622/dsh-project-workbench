## 2. 与设计稿的三处改动（本轮建议，需确认）

### 2.1 执行端顺序改成 DSH-first，Pi 留作对照

- 设计稿原定"内核用基础版 Pi"。
- **改动**：H0 先在 DSH 上实现方法层与记录，Pi 在 H2 之后作为对照/Durable 实验。
- 理由：DSH 已在本机常驻，具备 hooks（PreToolUse 可拒绝）、审批 seam、skills、agent presets、Agent Teams、worktree 工具、ralph、session-search、JSONL 会话持久化；Pi 还要先搭环境。
- 代价：设计稿里依赖 Pi `tool_call` 钩子的部分要用 DSH 的 hook / 原生插件替代；"Pi 是参考实现"这个定位留到多执行端阶段。
- 风险：DSH 是 0.2.0-rc 系，experimental 包接口可能变——本轮锁版本并记录 fingerprint。

### 2.2 记录只有一个真源：账本（agent-bridge），项目 `docs/records` 降为派生摘要

- 设计稿已把三份 schema 放在 `~/.agent-bridge/schemas`，但没有说清"项目记录"与"账本"谁真。
- **改动**：`~/.agent-bridge/ledger/*.jsonl` 为唯一真源（append-only、可校验）；项目 `docs/records` 只放人读摘要，由工具从账本生成，禁止手改。
- 理由：避免设计稿里已经出现的"同一份边界文本两份漂移"；`validate.py` 只认账本。
- 代价：要写一个"摘要生成器"（任务 D）；现有 `work-record` 习惯保持不变（它是人读件，不是账本）。

### 2.3 Agent Teams 作为"角色编排"的第一实现，不自写编排脚本

- 设计稿的"角色编排脚本"原打算自己写。DSH 的 Agent Teams 已提供：命名成员、durable 消息（崩溃/重启不丢）、共享任务板（依赖、领取、CAS、写路径重叠告警）、Lead 统一创建/打断。
- **改动**：H0 用 Agent Teams 充当方法层的角色编排；任务板状态作为台账事件源之一（H1 再接进账本）。
- 代价与限制：实验性；共享 cwd、无 worktree 隔离、无文件锁；任务 owner 不会自动释放；不能多进程共用一个团队。用"每线一个 worktree + 只读审查 + Lead 串行合并"来补。
- 结论：**它能当编排，但不能当隔离**。

### 2.4 上游基线：克隆 `deepseek-ai/deepseek-harness`（已拍板）

- **决定**：是，克隆上游当基线，路径 `~/projects/deepseek-harness`，`--depth 1`，pin `687f282e8625c6b8d11ff58211a90524be2e4317`（master，2026-10-17 push，MIT）。
- **H0 的用法**：只读 + 对齐接口（hooks、审批 seam、skill/preset 包结构、会话事件），**不改上游源码**；需要查实现时看这份基线，不查 `app.asar`。
- **H1 起**：要改上游时走 fork 分支（本地分支或 GitHub fork），提交边界与同步方式写进 ADR-003；不在 H0 里混改。
- **风险**：上游更新频繁（最近一次 push 10-17），本地基线会漂；ADR-003 要定「多久同步一次、同步时怎么验」。
- **附属动作**：新仓 README 里写明基线 commit；`git ls-remote` 与 `gh api` 的核对结果写进 ADR-003。

## 4. 契约（P0 必须先锁，A0/A1 产出）

### 4.1 ID、时间与引用

| 项 | 规则 |
|---|---|
| 记录 ID | `sur-YYYY-MM-DD-NNNN`（意外）、`les-YYYY-MM-DD-NNNN`（教训）、`asm-`（假设）、`prd-`（预测）、`ckp-`（检查点）、`stp-`（步骤）、`req-`（调用），沿用设计稿 |
| 两个时间 | `occurred_at`（发生）与 `recorded_at`（写入）；只追加，不改旧记录 |
| 更正 | 新记录用 `supersedes` 指向旧记录；旧记录保留 |
| 引用 | 一律用 ID 或"名字@版本"；不引用聊天里的说法 |
| 证据 | 每条记录 `evidence_refs` ≥1，写"可复现命令 + 输出摘要 / 文件:行 / 事件 ID"；"重跑通过了"不能当证据 |

### 4.2 两种记录格式

**意外记录**：沿用 `~/.agent-bridge/schemas/surprise-record.schema.json` v0（五类各自的必填 details 已定义），本轮修订点：

- `evidence_refs` 从"字符串数组"收紧为"至少一条以命令/文件/事件前缀开头的可核对引用"；
- 补 `supersedes`、`escalate`、`confidence`、`attempt` 字段（设计稿正文有、schema v0 没有）；
- 计划错强制 `assumption` 与回滚点；尺子错强制"谁修的"，且不允许等于实现方（与 I5 对齐）。

**教训条目（新建 `lesson-entry.schema.json` v0）**：

| 字段 | 规则 |
|---|---|
| `id` / `version` | id 不变；内容一改 version+1；旧版本保留 |
| `kind` | `lesson` / `standard` / `contract` / `example` |
| `status` | `proposed → shadow → active → retired` 单向；retired 后不再加载 |
| `form` | `gate` / `note` / `template` / `skill`；gate 还要写检查器路径与模式（observe/warn/block） |
| `scope` | `project` / `domain` / `general`；升级要来自新项目的意外记录作证据 |
| `applies_to` | `paths` / `symbols` / `tags` 至少一项；没有范围的不加载 |
| `evidence` | ≥1 条意外记录 ID |
| `metrics` | 回放验证后填 `r` / `f` / `p_lower`；`active` 前必填 |
| `body` | 规则 1–3 句 + 一个对的例子 + 一个错的例子 |

### 4.3 不变量（I1–I10 沿用，新增三条）

| 代码 | 检查 |
|---|---|
| I11 | 教训条目状态只能按 proposed→shadow→active→retired 走；`active` 必须有 `metrics` 与 ≥1 evidence |
| I12 | 教训的 `version` 单调递增，`supersedes` 指向同 id 的更早版本 |
| I13 | 每条"任务完成"事件（含团队任务板完成）必须引用 ≥1 条同任务的记录 ID |

### 4.4 写入点与校验点

```text
谁写      ：Lead / 实现代理 / 试点执行者（经 record 命令或 MCP 工具）
写哪      ：~/.agent-bridge/ledger/<project>.jsonl（唯一真源）
何时校验  ：写入时同步校验（schema+不变量，失败即拒），CI 每周全量复核
谁消费    ：validate.py（复核）、周报统计、H2 的上下文加载
失败怎么办：返回稳定错误码；不得静默丢弃；写失败视为没发生，用同 id 重试
```

- 写入口白名单：只允许 `record` 命令（或 `bridge_record` MCP 工具）写账本；禁止直接编辑 JSONL。
- 脱敏：记录里的 `observed` / 证据不得含 token、cookie、Authorization、页面原始 body；由写入前过滤 + `validate.py` 关键词扫描双保险。
- 敏感字段：`class=environment` 的 `fix` 可以写路径，不写密钥。

### 4.5 团队任务板 ↔ 记录

- 任务板每条任务在描述头写 `record: <预计记录前缀>`；完成时必须附 `record_id`（由 Lead/审查者核对，I13）。
- 任务板只用于"开发过程"；被开发框架自己的任务，将来（H1）才考虑把 board 事件写进账本。本轮先不混。

## 6. 验收（可检查的句子 + 命令）

1. **schema 正反例**：
   ```bash
   cd ~/.agent-bridge/schemas
   python3 validate.py surprise examples/surprise.good.json   # 退出 0
   python3 validate.py surprise examples/surprise.bad-plan-missing-assumption.json  # 退出 1，含 details.falsified_assumption
   python3 validate.py lesson   examples/lesson.good.json     # 退出 0
   python3 validate.py lesson   examples/lesson.bad-active-no-metrics.json          # 退出 1，含 I11
   ```
2. **技能决定规则**：40 条标注集、每题 3 次取多数；总准确率 ≥80%，"计划错被判成实现错"≤2 条，上报率 10–25%；混淆矩阵落盘。命令由 B 线提供（`python3 eval/run_surprise_eval.py --set <file> --runs 3`）。
3. **组合冒烟**：`dsh --profile harness --dump-config`（或等价）能看到 team/skill/hooks/preset 条目；`node test/harness-profile.mjs` 退出 0；一次真实会话里技能可被加载。
4. **记录达标**：试点两周后，`python3 tools/records_stats.py --ledger ~/.agent-bridge/ledger/<project>.jsonl` 输出：总记录 ≥30、类别覆盖五类、校验全过、缺证据 0 条。
5. **任务板一致**：所有 `completed` 任务都有 `record_id`；合并时无 write-scope 重叠告警。
6. **完整链路**：试点里至少一条"锁定预测 → 检查点 → 判定 → 意外 → 分类 → 教训条目"可从 ID 回放到原文。
7. **交接记录**：按 checklist 模板填（功能名/资源/上限/释放/监控/固定 workload/优化前后/残余风险），落在试点项目 `docs/records/`。

## 7. 开发组织：并行线 A–F

> 规则来自 checklist：先锁契约再并行；每线一个 worktree；任务书头两行 `depends:` / `verify:`；执行者不宣布通过；审查者换上下文/模型；合并与真机验证串行。

| 线 | 内容 | 依赖 | 写范围（worktree 内） | 不能改 |
|---|---|---|---|---|
| **A（串行）** | 仓与契约骨架：ADR-001/002、记录格式、任务书校准 | 无 | 新仓 + `~/.agent-bridge/schemas` | 既有 schema 语义（只能加不能撤） |
| **B** | 意外分类技能包 + 评测 harness + 标注集找回/重建 | A | `<repo>/skills/**`、`<repo>/eval/**` | 记录格式、组合文件 |
| **C** | DSH `harness` 组合：profile、角色 preset、团队配置、独立 hooks、技能挂载 | A | `<repo>/profiles/**`、`~/.dsh/.agent-presets/harness-*` | 现有 desktop patch、Orca hooks |
| **D** | 记录写入管线 + 统计 + CI 校验 | A | `<repo>/tools/**` | schema 语义、组合文件 |
| **E** | 真实试点（2 周） | B、C、D | 试点项目 `docs/records/**`、账本 | 不修业务代码 |
| **F** | 文档/CI/交接模板/README | A（可最早起） | `<repo>/docs/**`、`.github/**` | 不碰实现 |

串行项（不并行）：契约与记录 owner、错误码、试点验收、最终合并、真机验证。

## 8. 智能体团队在这轮怎么用

### 8.1 适用性判断（先过五条）

1. **能切成不写同一文件的块**：B（skills/eval）、C（profiles/presets）、D（tools）、F（docs/CI）天然分目录——满足。
2. **每块足够大**：B 与 D 各 1–2 天，C 半天到 1 天——满足。
3. **块间少来回**：靠 A 的契约隔开，B/C/D 互不依赖——满足。
4. **完成标准可判定**：§6 全是命令——满足。
5. **有一块只读**：审查者（契约审查 + 记录质量审查）——满足。

结论：**H0 适合用团队，但只用 3 条实现线 + 1 只读审查，先试点不铺满。**

### 8.2 角色与组成

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| Lead | 主会话 | 锁契约（A0/A1）、建 worktree、派单、串行合并、最终验证 | 不把契约设计交给队友 |
| 实现 B | teammate | 技能包 + 评测 harness | 不改 schema/组合 |
| 实现 C | teammate | profile/preset/team/hooks 配置与冒烟 | 不动 desktop patch 与 Orca hooks |
| 实现 D | teammate | `record` 命令、统计、CI | 不改 schema 语义 |
| 审查者 | teammate 或 `subagent`（换模型/上下文） | 只读审查：契约一致性、证据是否可复现、写范围越界 | 永不写文件 |
| 试点执行 | Lead 或独立人 | 跑两周试点、写记录 | 不能同时当试点审查者 |

成员数建议 **5**（Lead + 3 + 审查），上限 6（F 线下沉到各线，不单独占人）。

### 8.3 任务板与写范围（Agent Teams 纪律）

- 每个任务卡：`depends:` 第一行、`verify:` 第二行、`write_scope:` 第三行（worktree 路径或子目录）。
- `blocked_by` 用任务板表达：B/C/D/F 都 `blocked_by` A1；E `blocked_by` B/C/D。
- **用目录隔离代替锁**：Lead 先建 4 个 worktree（每条线一个），队友只在自己的 worktree 里写；跨线只读。
- 队友之间可以互发消息，但**本轮约定协调只走 Lead + 任务板**，避免绕开审计。
- 执行者不宣布通过：`verify` 由审查者或 Lead 在独立上下文里跑；合并只由 Lead 串行做。
- 团队任务板状态不写账本（H1 再接），但每张卡完成时在描述里附 `record_id`，由 Lead 核对。

### 8.4 什么时候**不**用团队

- A0/A1 契约（必须一条流水线想清楚）。
- 合并与真机验证（串行）。
- 试点验收（避免自己验自己）。
- 任何需要"同一份大文件"的写入（如 `docs/HEADLESS.md` 那类；本轮新仓 docs 分开写）。

### 8.5 成本与风险

- 协调开销：Lead 每天两次收口（早派单/晚合并），否则任务板会腐烂。
- 合并风险：4 条线改动都新文件时冲突小；一旦要改 `~/.dsh/profiles/desktop/cordis.patch.yml` 这类共享文件，必须 Lead 单独做。
- 内存/CPU：4 个 worktree 同时跑测试会叠负载；B/C/D 的 verify 只跑子集，全量由 Lead 串行跑。
- experimental API：队友和主会话必须锁同一 DSH 版本；升级另行一轮。

## 12. 风险与停止判据

| 风险 | 判据 | 应对 |
|---|---|---|
| 标注集找不到 | A0 第一天结束时 | 从 `docs/records` 重建 40 条（抽"结果与预期不一致"的情况），先标注再跑；仍不行则技能验收改为人工抽检并降级 |
| 技能达不到 80% | 两次迭代后 | 按设计稿决定规则：改分类顺序与证据要求，换新 40 条；仍不行则 H0 只交付格式与管线，技能转 H2 |
| DSH experimental 接口变动 | 任何升级 | 锁 0.2.0-rc.2；改动进 ADR；不在本轮升级 |
| hooks 与 Orca hooks 冲突 | C 线冒烟 | 独立 configPath；不改 `~/.dsh/cordis.patch.yml` 的 Orca 段 |
| 记录多头写 | 第一次盘点 | ADR-001 定单一真源；项目 records 只读派生 |
| 团队合并冲突 | 每次合并 | 目录隔离 + 只读审查 + Lead 串行；共享文件只在 A 线改 |

| 时间被日常打断 | 每周复盘 | 最小两天版先落地；试点可缩到一周（≥15 条）但 H0 不算"过" |
