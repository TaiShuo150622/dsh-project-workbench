# 独立上下文组装器：认知科学依据、prefill 成本与验收设计

> 公开整理版 · 整理日期：2026-11-06 · 源版本：研究笔记；2026-10-31。
> 保留个人通用研究、方法和公开来源；已省略公司案例、项目专属实现、个人身份与会话材料。
> 本次仅整理文本，未重新运行原实验、复测宿主兼容性或更新外部资料；历史结论仍受原研究范围限制。


研究目标：由独立模型主动从记忆中组装执行器的工作上下文，使执行器在新任务第一轮更快、更准确地开始行动。记录分类、跨会话问答和恢复现场是支撑能力，不能替代这个目标。NVIDIA Auto Ontology 与自动生成／演化本体均属本次研究范围；具体实现分析另见配套研究笔记。

本文只提供研究证据与待验证方案；未运行模型、性能基准或产品测试，没有改动代码、配置、采集器和部署。

## 1. 认知科学能支持怎样的设计，不能证明什么？

### Takeaway

有用的启发是区分三件事：长期保存了什么、当前任务需要激活什么、谁负责选择与更新这些内容。它支持把上下文组装当成持续控制任务，而不只是一轮结束后的摘要。不过，人类认知理论不能证明「额外小模型 + 本体」一定优于普通检索，也不能直接给出 token 预算、模型大小或自动化权限。

### Cited Findings

### Inferences

以下是本项目设计推论，不是上述论文在 AI 系统上得出的实验结论。

1. **工作上下文应是一份面向当前动作的状态，不是长期记忆的缩小副本。** 执行器当前需要知道目标、硬约束、已经确认的事实、未解决的问题、应避免的旧错误、接下来可以做什么；与本轮动作无关的旧讨论可保留索引入口。独立模型的职责是决定哪些证据现在值得占用上下文，并检查必要内容是否齐备。
2. **组装器需要看到任务与反馈。** 如果它只在每轮后摘要、下一轮机械发送同一摘要，就没有实现任务驱动选择。应在新请求、目标变化、出现意外、执行器报告证据不足时重新评估；新请求进入之前能预先做的是抽取和索引，通常无法预知完整任务上下文。
3. **存储时保留将来的检索线索。** 除主题标签，还需保留任务目标、项目／版本／环境、实体、说话人、断言状态、有效时间、来源范围、失败条件和被替代关系。同一段历史在「排障」「发布文档」「设计新模块」任务中价值不同。向量相似不是唯一的任务相关性。
4. **快写入、慢整合、按需激活应分开。** 新纠正和新事实即时进入可查询的事件／断言层；实体合并、类别拆分、关系规则变化较慢地形成候选版本；每个新任务读取一个明确版本，并直接叠加最新的必要纠正。慢整合不能成为忽略最新用户指令的理由。
5. **细分类别的价值要落到动作上。** 「排障」拆成依赖、权限、数据、版本等，只在它改善过滤、解释、后续行动或迁移时有价值。将每个句子拆成更多类，不自动增加执行器的可用信息。
6. **把控制职责写成可检查的接口。** 组装结果至少应区分 `task/constraints`、`verified_evidence`、`uncertainties/conflicts`、`source_refs`、`memory_version` 与 `coverage_gaps`。组装器可以提出下一步，但不把自身推测升格成用户决定；执行器应能按来源补读。这里的字段是讨论示例，不是已落盘的新 schema。

一个非敏感例子：用户要「继续处理上次验证失败」。按关键词找回“验证”不足以支持行动；组装器要区分失败发生在哪个 checkout、当时缺依赖还是被测物错误、哪些测试没跑、用户是否授权安装依赖。只传“上次验证未通过”更短，却可能让执行器从错误动作开始。

### Gaps

- 这些认知理论中「系统」「控制」不等于必须存在一个中央小 LLM；规则、检索器、重排器、模型和执行器协作都可能实现对应职能。
- 人类短时容量不能换算成某个固定 token 数；神经系统慢学习不能直接等同数据库 schema 迁移；外部记忆库不意味着修改模型权重。
- 本任务最需要验证的是独立组装是否比廉价检索和固定上下文更有收益，而不是找到一幅与大脑形似的架构图。

## 2. 短上下文能否降低第一轮 prefill、TTFT 与总成本？

### Takeaway

可以形成可检验假设，但不能只看执行器输入 token 变少。还需计算取回与组装成本、实际复用的前缀 KV、主模型排队、缓存传输、资源争用和失败后的补读。一次新任务的第一轮也可能命中已有系统／项目缓存；第一轮不等于冷缓存。

一个先决条件是宿主必须允许控制执行器实际接收的消息。如果 before-step 插件只把检索记忆追加进去，而原始完整 transcript 仍照常发送，它本身不会减少输入，反而会增加输入；它可能改善准确性，但没有实现这里的 prefill 压缩路径。真正替换历史，需要受控的消息构造／上下文压缩接口，或启动带精简上下文的独立 Worker；后一种做法还要计入失去既有会话前缀／KV 复用的成本。这是架构上的条件判断，不是已核实某个当前宿主必然不支持替换。

### Cited Findings

- vLLM 的 [Automatic Prefix Caching 文档](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)说明：相同前缀可复用 KV，收益集中在 prompt processing／prefill；它不减少生成新 token 的 decode 工作，没有共享前缀或 decode 占主导时收益有限。
- vLLM 的 [Prefix caching 设计文档](https://docs.vllm.ai/en/stable/design/prefix_caching/)说明：块标识包含块 token、父块哈希以及相关附加键；父哈希对应此前全部前缀，该设计按完整块缓存。缓存块还会被逐出。因此，后部文本相同不足以保证其 KV 可复用。
- Zheng 等的 [SGLang 原论文](https://arxiv.org/pdf/2312.07104)（2023 提交，核读 2024 v2）在 RadixAttention 中用 radix tree 组织共享前缀，并讨论 LRU、缓存感知调度和复用比例。缓存利用率与请求顺序、容量和调度有关；论文特定实验的吞吐提升不能当成目标项目的速度预测。
- vLLM 的 [Optimization and Tuning 文档](https://docs.vllm.ai/en/stable/configuration/optimization/)说明：chunked prefill 可以把 prefill 与 decode 混合调度，配置选择会影响 TTFT 与 token 间延迟的取舍。因此，只测单个空闲请求不足以说明并发时的用户体验。
- Liu 等的 [Lost in the Middle](https://arxiv.org/html/2307.03172v3)（2023）在多文档问答及键值检索任务中发现，相关信息位置和输入长度会影响其测试模型的表现。这支持评估干扰和位置，不能证明今日执行器必然有同样幅度的退化，也不能推出越短越准确。

### Inferences

#### 2.1 应区分的量

| 量 | 这里的含义 | 不能用什么代替 |
|---|---|---|
| 执行器 prefill | 服务端处理本次输入、利用或建立相关状态的阶段；具体计时按引擎定义 | 不能直接用所有输入 token 数推导时间 |
| 执行器 TTFT | 请求发给执行器后，到它返回首个 token | 不包含请求发出之前的检索／组装 |
| 用户端首个有效输出延迟 | 用户请求到执行器首个有用 token 的总时间 | 组装器发一句“正在处理”不能算完成指标 |
| 首个正确动作延迟 | 到执行器第一次选择符合目标、证据与约束的动作 | 更快发出一个错误 tool call 不是改进 |
| 完整任务延迟与成功率 | 含补读、工具、重试、纠正的最终工作结果 | 只测 TTFT 无法覆盖后续错误成本 |
| KV cache hit | 计算状态复用 | 不是找到了正确记忆，也不是证据充分 |
| 语义检索 hit | 取回了任务需要的记忆证据 | 不是计算缓存命中；两者需分别测量 |

记录全部输入 `N`、实际已缓存输入 `K` 及未缓存部分 `N-K`。即使 `N_new < N_base`，也可能因为 `K_new` 明显减少，导致 prefill 收益小于预期甚至反转。未缓存后缀仍需使用前缀上下文；缓存读取和模型结构也有成本，因此不应假设 `P` 严格等于 `c × (N-K)`。

#### 2.2 时延盈亏条件：只给公式，不捏造速度

设 baseline 为 `B`，加入独立记忆组装器的方案为 `M`：

```text
T_user_to_first(B) = A_B + Q_B + P(N_B, K_B; θ_B) + F_B
T_user_to_first(M) = A_M + Q_M + P(N_M, K_M; θ_M) + F_M

方案 M 降低用户首个有效输出延迟，当且仅当：
P_B - P_M > (A_M - A_B) + (Q_M - Q_B) + (F_M - F_B)
```

- `A`：用户请求到执行器发出之间的临界路径，包括检索、组装模型自己的 prefill 和生成、校验、必要的传输；并行工作按实际临界路径算，不能把重叠时间重复相加。
- `Q`：执行器排队等待。
- `P(N,K;θ)`：执行器实际 prompt 阶段耗时。`θ` 包含模型、硬件、负载、缓存位置及引擎策略，实际定义须与监控一致。
- `F`：prefill 完成后至首个有效 token 送达的剩余耗时，如采样和传输；不假定每个引擎都需要另算一个完整 decode step。

这是分解与决策条件，不是性能定律。若没有服务端分段计时权限，就报告实际可见的端到端延迟、执行器 TTFT 和 cached token 指标，不能把 TTFT 全称作 prefill。

在同一 GPU 上运行小组装器，可能改变执行器的 `Q`、`P` 和缓存容量；“模型小”不代表额外耗时可忽略。组装器每次重新读完整历史，也可能只是把长输入问题搬到另一处。应优先让它读取分层索引、候选证据和任务状态，必要时再打开原件。

若每轮后台抽取让下一任务的在线 `A_M` 降低，这是真正可能的收益；但后台模型费用与索引维护不能从成本账上消失。提前猜测下一任务而投机生成上下文，要单独计算命中率、废弃工作和过期风险。

#### 2.3 成本条件与缓存布局

```text
C_total(M) = C_retrieve + C_assembler + C_executor
           + C_writeback + C_maintenance_amortized + C_retry

若服务商按 token 分类计费，可单独计算：
C_executor = u × (N-K) + c × K + o × O
```

`u/c/o` 必须采用实际服务的未缓存输入／缓存输入／输出单价，`O` 是输出量；无此计费口径时不用该式。自部署应比较 GPU 时间、设备占用和实际货币成本，不能把 API token 单价当计算耗时。最终还要看每个成功任务的总成本，避免“便宜但经常失败”。

讨论用的布局候选是：稳定系统与工具约定、稳定项目事实前缀、带版本的任务证据、当前请求。稳定内容保持确定序列化，动态内容不要无谓地插入很早的位置。该建议仍需与信息位置影响一起测试：不能为了 cache hit 固守过期事实，也不能为了把相关材料放最前面无代价地改动整个前缀。

| 缓存条件 | 对组装方案的预期假设 | 必测风险 |
|---|---|---|
| 冷 KV，模型和索引已就绪 | 删去无用输入较可能降低主模型 prefill | 组装耗时吃掉节省 |
| 稳定系统／项目前缀已缓存 | 主要节省发生在动态未缓存部分 | 原 baseline 很长但已经便宜 |
| 同任务完整前缀热缓存 | 重复请求可大量复用 | 组装重写、排序漂移降低复用 |
| 早部记忆／规则更新 | 后续缓存可能失去可用共享前缀 | 旧缓存／旧事实失效必须正确 |
| 并发执行、组装器共用设备 | 取决于调度与资源占用 | TTFT 改善但 p95／吞吐恶化 |

冷模型启动、冷 KV、冷检索索引是三种不同条件，应分开注明。后台写回通常不阻塞当前首 token，但仍可能争用下一请求的资源。

### Gaps

- 尚未确定本系统执行器的服务入口、具体模型、缓存策略、可观测指标和部署位置；不能给出可信的 token 阈值、毫秒收益或省钱比例。
- NVIDIA Auto Ontology／自动生成本体是否适合放在在线临界路径，取决于具体实现和测量。更丰富的图检索也可能增加 hop、查询和重排成本。
- 上下文减少有两条潜在收益：降低计算量、减少干扰；也有两类独立失败：漏证据、失缓存。不能拿其中一个指标为另一个背书。

## 3. 如何证明它改善了新任务起步，而非只会回答旧会话问题？

### Takeaway

评估单位应是「在时间截断的真实任务起点，执行器能否带着足够且正确的依据开始行动并完成任务」。比较必须包含廉价检索基线，并把独立组装与本体贡献拆开。下述是拟定方案，尚未执行。

### Cited Findings

评估分别使用上述官方文档明确的 prefill／decode 和缓存概念，以及长上下文论文展示的位置干扰维度；具体任务集、方法分组和指标均为本项目提出，不冒充已有论文实验结论。[vLLM APC](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)、[SGLang 论文](https://arxiv.org/abs/2312.07104)、[Lost in the Middle](https://arxiv.org/abs/2307.03172)

### Inferences

#### 3.1 方法消融

| 方法 | 改变什么 | 回答哪个问题 |
|---|---|---|
| B0：现行固定交接／最近历史 | 维持当前可重现基线 | 对今天的系统是否有净改善 |
| B1：规则过滤 + 词法／向量检索 | 在同等上下文预算下选择材料 | 额外模型是否真的必要 |
| M1：独立小组装器，事件与元数据 | 按任务选择、去重、处理冲突与检查缺口 | 组装控制本身有没有收益 |
| M2：M1 + 已冻结版本的本体检索 | 加实体、关系、层级与路径证据 | 本体是否带来新增收益 |
| M3：M2 + 历史材料形成的本体演化 | 允许拆类／合并，任务开始前版本冻结 | 自动结构演化能否泛化且不破坏旧任务 |
| 人工必要证据与无记忆对照 | 人工证据仅作参考；无记忆作负对照 | 检索问题与执行器使用问题分别在哪里 |

固定执行器、工具权限、生成设置和任务验收规则；主比较采用相同输入预算，另画预算变化的成功率—延迟—成本曲线。组装器输出更短但遗漏约束不能称为成功。不要为了匹配 token 数而给较短方案填无关内容；记录实际用量。

#### 3.2 任务与运行条件

任务至少覆盖：跨会话继续一个未完成工作、在已有约束下开展新工作、遇到相似旧失败但当前根因不同、旧决定已被新决定取代、材料相互矛盾、没有相关记忆且需要现查。验收重点是下一步行为，而非只问“某次会话说了什么”。

每个方法在冷 KV／稳定前缀热缓存／完整重复前缀／早部更新导致失效条件下对照；另标识索引冷热、低负载与典型并发、组装器和执行器是否共用设备。可先用小型配对集排除明显无效方案，再扩充到工作负载，不预先声称需要某个未经估算的样本数。

必须把记忆截断在任务开始前，按会话／时间划分留出集，防止把后来的答案或修复结果提前交给组装器。不同方法应有独立缓存命名空间或一致的冷启动／预热流程，避免前一个方法偷偷替后一个预热。此处仅是实验要求，没有执行任何服务端清缓存操作。

#### 3.3 验收与诊断指标

| 维度 | 拟测指标 | 判别目的 |
|---|---|---|
| 首轮行为 | 首个动作正确率；已知约束违背率；是否反复要求用户重述已有事实 | 是否真正改善起步 |
| 证据齐备 | 必要来源覆盖率；全部必要证据齐备的任务比例；来源可追溯率 | 压缩是否丢了前提 |
| 证据质量 | 无关材料比例、过期事实使用、冲突未标注、提议误作决定 | 分类准确不等于事实可靠 |
| 记忆命中／漏检 | 按稳定 source ID 计算取回、进入上下文、被正确使用三个阶段 | 区分检索、组装、执行器失败 |
| 计算缓存 | 实际 cached token、输入总量、未缓存量、复用比例 | 独立于语义 hit 测量 |
| 在线延迟 | 检索／组装／校验临界路径；执行器排队、prefill（可观测时）、TTFT；用户端首个有效输出与首个正确动作 | 防止只报告局部加速 |
| 完整任务 | 独立验收成功率、总耗时、补读次数、重试、回退率、单位成功成本 | 首轮收益是否保留到完成 |
| 稳定性 | 配对任务差值、p50／p95、按缓存和任务子类拆分；必要时给区间估计 | 防止平均数掩盖慢尾和局部退化 |
| 本体演化 | 旧任务回归、迁移后来源可达性、旧版本重现、拆类后仍可回答原查询 | 更细结构是否值得维护 |

证据集合和行为验收应由独立规则、任务原件或人工审核建立，不能让组装器给自己的输出打“充分”分就算通过。对生成的答案做相似度评分也不能替代实际任务验收。

一个有诊断力的失败分解是：必要来源是否在库 → 是否被检索到 → 是否被选入上下文 → 是否保留关键限定词 → 执行器是否正确使用 → 最终动作是否通过验收。每一级保留来源 ID 与阶段回执，才能知道该改 ontology、retrieval、assembler 还是 executor。

如果 M2 不优于 M1，本体可继续作为后台组织工具，不必强制进入每次在线调用；如果只在冷缓存时收益明显，应评估有条件路由。必要约束缺失、冲突未消解或过期状态无法确认时，补读或交回执行器调查，是合理结果；不能为达到 token 预算凭空填补事实。
