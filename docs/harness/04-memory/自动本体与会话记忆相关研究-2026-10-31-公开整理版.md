## Auto Ontology 能否直接为会话建立并递归细分本体

### Takeaway

若用户指 NVIDIA/auto-ontology，当前版本主要把关系数据库的物理表列转成业务语义目录并支持查询。它能拆分表里的业务概念、维护属性和关系，但本次查证不足以认定它提供“对逐轮会话自动生长并递归拆类”的现成运行时。适宜借用其语义映射与验证思路；会话解析、类型演化、证据与版本协议仍需单独设计。

### Cited Findings

- **身份与版本。** NVIDIA 官方仓库名为 Auto Ontology，当前 `main` 查得提交 `98101384ed92d0ccbe208d189871091c65b3ba38`，提交时间 2026-10-28。README 把它定位为企业元数据的语义上下文层，支持数据库查询、MCP/CLI/API，目录及语义层存 Postgres。该定位区别于 AutoSchemaKG。— [官方 README](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/README.md)，[提交](https://github.com/NVIDIA/auto-ontology/commit/98101384ed92d0ccbe208d189871091c65b3ba38)
- **输入和拆分边界。** `RawTableTermsResult` 接收单个物理表的 Term 与列分配；提取提示词强烈偏好一表一 Term，只有确属两个不相关实体的连接表才考虑第二个，禁止按元数据/生命周期/审计字段把单实体切开；每列分配恰一个 Term。这是在消歧关系表业务概念，不是按会话问题自动建立任意深度类别树。— [models.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/semantic/models.py#L46)，[term_extractor.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/semantic/term_extractor.py#L32)
- **`IS_A` 不能当成已实现细分的证据。** `semantic/constants.py` 声明 `IS_A`、`PART_OF`；本次 GitHub code search 对 `REL_IS_A`、`REL_PART_OF` 都只返回该定义文件。语义表结构实际包含 Term、Table→Term、ColumnAttribute→Term、语义外键等。已读 `term` schema 没有父类型字段，属性只归属一个 Term；未发现对应自动递归细分执行路径。此结论限于查到的版本和路径，不等价于证明所有历史版本从未有过该能力。— [常量](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/semantic/constants.py#L29)，[schema.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/dal/schema.py#L452)
- **增量与稳定身份并非通用语义归并。** 编译器处理尚无 Term 的表，LLM 可并行，提交按规范表序列排列以确定同名 Term 的归属。提交阶段使用 table-private Terms，名称冲突会加限定名称，避免随便把同名概念合并。这有利于确定性，却不是跨会话同实体解析或任意类别 merge/split 的证明。— [pipeline.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/semantic/pipeline.py#L126)，[visit_enter.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/semantic/visit_enter.py#L914)
- **修改与发布存在边界。** 官方建模说明要求问题契约、来源和稳定 ID，并明确没有直接创建空 Term 的公开端点、没有完整的直接结构关系修改流程。结构变化应通过有范围的 native model export/import。官方发布说明又明确认证字段不构成原子的审阅/发布系统，现有返回成功也不等于精确持久化一致。— [modeling.md](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/skills/nvidia-ontology-management/references/modeling.md)，[publication.md](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/skills/nvidia-ontology-management/references/publication.md)
- **数据库版本不等于本体版本。** `dal/schema_version.py` 验证 Alembic 数据库迁移版本与软件是否一致；不能把这当作概念版本、类型拆分历史和事实有效期已经建好的证据。— [schema_version.py](https://github.com/NVIDIA/auto-ontology/blob/98101384ed92d0ccbe208d189871091c65b3ba38/auto_ontology/dal/schema_version.py)
- **更接近文本自动诱导的相邻项目：AutoSchemaKG。** 论文先抽实体、事件及关系，再从实例和邻接上下文抽象概念，产生不同抽象层的概念短语和映射；代码提供实体/事件抽取→概念 CSV→GraphML 的分阶段流程。这里的 dynamic schema induction 主要指从语料生成 schema，不能自动推成在线受控拆类/旧实例迁移/回滚系统。论文 v1 报告使用 Llama-3-8B-Instruct 处理大语料，说明小模型能参与这一类任务，但不是我们的中文会话准确率证据。— [AutoSchemaKG 论文 §3 与 §4](https://arxiv.org/html/2505.23628v1)，[开源实现](https://github.com/HKUST-KnowComp/AutoSchemaKG)

### Inferences

以下为本次方案推论，非上述项目现成功能承诺。

1. “更细”至少有四种不同操作：把一轮拆成多个可证据定位的记忆单元；给同一单元增加多维分类；将一个主题细分子主题；增加新实体类型/关系/约束。它们应使用不同操作，不能统一叫 split。
2. 建议保留稳定的记录骨架，例如来源、轮次、作者、时间、证据范围、事实/判断/猜测状态。项目/问题域/研究主题允许多标签或 DAG 归类；关系可表达 `supports`、`contradicts`、`supersedes`、`depends_on`、`caused_by`。纯树不能表达一项决策同时涉及存储和权限。
3. “分类层”可以自动适应，“本体演化层”宜慢一点：先提议新类/别名/合并/拆分→用原始例子和反例验证定义→评估既有检索是否受损→分配稳定类型 ID 与版本→迁移或重投影受影响实例→保留旧版本映射和回滚。不要每一轮让小模型自由重写整棵树。
4. 拆类理由应是可区分的定义、稳定出现的实例差别或真实检索需求，不能只靠类别计数大、embedding 距离或模型觉得名字更漂亮。暂不确定的单元允许多归属、未归类和候选类型。数值阈值需要用项目数据校准，落地时按仓规登记超参。
5. 稳定 ID 与名称分离；类别改名不应改变对象身份。split 时保留父类和版本映射，重判历史成员；merge 时保留别名与旧 ID 重定向，不覆写原始会话。schema 定义变更和实体事实更新应分开审计。

### Gaps

- 本文的 NVIDIA Auto Ontology 分析仅适用于所注明项目与提交，不应推广到同名系统。
- 未找到 NVIDIA 这一版本的会话导入→自动归类→递归拆类→实例迁移→回滚的完整示例；目前不应把拼接这条链描述成配置即可完成。
- 没有运行 NVIDIA 或 AutoSchemaKG，也没有测量中文、编码会话、歧义指代、工具噪音或大规模增量性能。
- AutoSchemaKG 的 arXiv v1 摘要与 ACL 2026 定稿搜索结果中 schema 对齐百分比不同；本笔记不采用该百分比作结论，以避免混版本。

## 哪些论文和开源项目最值得借鉴

### Takeaway

最贴合的组合是：Graphiti 的逐步摄入、来源和时间语义；A-MEM 的可演化记忆单元与连接；AutoSchemaKG 的从文本诱导概念；LongMemEval 与 UnifiedMem 的评估方法。它们各解决一部分问题，没有一个已经证明“便宜模型＋自动本体”会无条件胜过结构化平面记忆。

### Cited Findings

### Inferences

- 推荐保留同条件的三条基线：现有记录检索；原文＋结构化记忆＋全文/向量；再加本体/图。比较“真的能找回当时证据、识别已被纠正的结论、回答跨轮问题”，而非只比较抽出了多少节点。
- 小模型承担“证据有明确落点的增量抽取与归类”可行性较高；不应让它猜执行代理未公开表达的内心理由。执行代理当场报告的决策理由仍是独立来源，后验观察者推测必须显式标识。
- 更强模型用于低频难题：跨会话身份冲突、新类型定义、合并/拆分审查、长链矛盾；是否升级可按规则验证失败、未归类、来源冲突等信号决定。不要仅信模型自报 confidence。
- 评估应拆成来源定位、事实精确率/遗漏、纠正覆盖、时序、类目稳定、检索召回、最终回答、成本/延迟。新模式应能重放旧原件，并用固定样本比较前后，不要只凭“看起来更聪明”。
- 特别应有负例：同名不同项目、计划未执行、执行了但失败、用户否定过的旧结论、假设被当作事实、工具输出里含提示注入、相对时间、单轮多主题、中断后补写、重复 hook、无权读取的来源。图谱关系本身不是授权或可信级别。

### Gaps

- 没有给出最便宜模型名称或质量门槛：这些需要对当前本机/远端模型和中文记录做实测，不能由论文默认模型代替。
- 未用 LoCoMo 的厂商榜单作排序，也未对候选仓库完整测试、依赖安全、性能和发布节奏进行审计。Graphiti、Mem0、NVIDIA 当前有可核实近期提交；A-MEM/AutoSchemaKG 在本文定位为研究参考，不承诺维护 SLA。
- 不建议此时引入训练型记忆管理策略；先把证据链、触发可靠性与检索收益测出来。

## 每轮触发、数据存储与本体演化如何组合

### Takeaway

建议采用“不可变证据＋可重建语义层＋可替换检索索引”。每轮 hook 负责可靠提交待处理事件；小模型异步抽取/归类；本体演化独立调度。先按单机还是多机/多人决定事务库，再按查询需求决定是否需要独立图数据库或 RDF，而不是因为有本体就必须上图数据库。

### Cited Findings

- SQLite WAL 允许读写并行，但所有进程必须在同一主机；单个 WAL 仍只有一个写者，不能把数据库文件放网络文件系统当多机共享服务。— [SQLite WAL](https://www.sqlite.org/wal.html#concurrency)
- PostgreSQL `jsonb` 支持索引，但不保留空白、键顺序或重复键。它适合结构化派生记忆；如果要求逐字原件，应单独保留原始字节/文本与哈希，不能声称 `jsonb` 就是字节级归档。— [PostgreSQL JSON types](https://www.postgresql.org/docs/current/datatype-json.html)
- SHACL 的职责是用 shapes 验证 RDF 图满足约束；它不是从会话自动发现概念的算法。— [W3C SHACL](https://www.w3.org/TR/shacl/)
- Graphiti 源码与论文体现了原始 episode、派生事实、可回溯来源分开的可行实现；但其图后端与服务边界并不替我们确定事务主库。— [Graphiti](https://github.com/getzep/graphiti)，[Zep 论文](https://arxiv.org/html/2501.13956v1)

### Inferences

以下全部为提议架构，不是本项目已经实现的能力。

**1. 触发和可靠性。** 宿主的 turn end/Stop 只发事件，先完成原始片段的本地可靠持久化，再把 extraction job 放队列；主对话不要等待本体重算。用宿主/会话/轮次/源版本组成幂等身份；实际 key 和重试阈值待设计。防重复、顺序错乱、录到一半、子代理重复输出与观察者自身触发递归。轮末事件需要配合周期补扫和会话结束兜底，具体 hooks 必须按 DSH/Claude/Codex 各宿主能力验证。

**2. 双速度处理。** 每轮处理当前增量＋必要的前几轮上下文＋会话状态卡＋召回的相关既有记忆，避免每轮重读全部历史。小模型只生成带来源 span 的候选结构；确定性校验来源是否存在、类型/字段是否合法、ID 是否跨项目串线。较低频整理器才讨论新的类别定义和关系结构。失败保留原件和待处理任务，从断点继续。

**3. 四层存储职责。**

| 层 | 保存内容 | 推荐起点与迁移条件 |
|---|---|---|
| 证据原件 | 原始事件/转录、附件引用、哈希、轮次/来源坐标 | 保留现有账本；append-only 清单＋压缩对象；敏感原文独立权限 |
| 语义记忆与任务 | assertions/events/entities、出处、有效期、状态、抽取器/模型版本、幂等队列 | 单机可 SQLite＋单写者；多机/多人、并发写和权限要求提高时 PostgreSQL |
| 本体注册 | 稳定 type/relation ID、定义、别名、约束、版本、迁移映射、审核记录 | 初期版本化定义＋事务表；需要跨系统语义互操作/标准推理才考虑 RDF/OWL＋SHACL |
| 检索投影 | 全文索引、向量、图关系、摘要、分类导航 | 可从前面重建；先全文/向量/关系表，需要复杂遍历并测到收益再增图后端 |

**4. 记忆单元最小语义。** 一条记忆应回答谁在何时说/做/确认了什么，适用于哪个项目/环境/时间，来源在哪里，是 observed/asserted/inferred/proposed 还是已执行，是否被后续结论取代。区分事实发生时间与记录/识别时间；将“作出更改的提案”和“更改已生效”分开。模型版本与 schema 版本分开记录。

**5. 删除与失效。** 为审计而保留旧事实的原则不覆盖真实删除要求；原件保留期、敏感数据屏蔽和索引删除传播需独立讨论。正常知识更新先标失效/取代，不抹去当时发生的事情。重新抽取时不能把已撤销记忆复活，也不能把旧模型猜测升级为事实。

**6. 推荐试验顺序。** 先选择经过同意的已有样本构造问题/证据金标→接每轮候选记录的影子输出→测平面记忆基线→引入可演化主题/关系→用少量真实拆分/合并案例评估迁移与检索→再决定专用图数据库、模型路由及是否替代原流程。正式记录和知识原件保持各自权威边界；候选方案须讨论后实施。

**7. 需要用户讨论的选择。** 系统的首要收益是事后审计/检索还是主动给下一轮供上下文；范围是目标项目还是跨项目；小模型运行在本地还是授权远端；是否允许候选类自动生效及哪些改动需人确认；多用户/多机器规模；原始会话保留/删除政策；优先改善的具体检索问题。先选目标问题，才能决定本体的粒度是否有价值。

### Gaps

- 当前宿主 hook 生命周期、所有转录格式及仓库已有数据库需由本地调研线给出，本文不把 Claude Stop 等同于所有宿主的轮末事件。
- 存储推荐没有容量测量、成本估算和压测。目录/索引/图的数据量、摄入频率、读写并发未测之前，不选服务数量或部署规模。
- 本次同时看到新版 Mem0 改用只追加，以及研究中不同配置对图收益的差别，所以不能仅按“模型更小、分类更多”判成功。质量收益与可靠证据回放才是需要实验回答的问题。

## 补充 自动本体学习不限于知识图谱抽取

### Takeaway

本节同时考察 NVIDIA 实现与一般自动生成本体。一般本体学习需要分别解决术语归类、上下位层级、非层级关系，以及约束和逻辑一致性；相似度聚类只是候选生成步骤，不能替代这些判断。

### Cited Findings

- **LLMs4OL 与 OntoLearner。** LLMs4OL（2023）将术语类型识别、taxonomy discovery 和非层级关系抽取分开评估。后续 OntoLearner（2026-07-02）提供可复用本体、标准数据拆分、检索增强学习管线与评估；论文 §3–4 的主线是已有本体上的学习/补全，不是每轮自主重构运行时。其功能表将词汇映射/对齐标成规划中，也未宣称已有本体编辑器。— [LLMs4OL](https://arxiv.org/abs/2307.16648)，[OntoLearner 方法](https://arxiv.org/html/2607.01977v1#S3)，[开源库](https://github.com/sciknoworg/OntoLearner)
- **OntoGPT/SPIRES。** 沿用户给定 LinkML schema 递归抽取，一次提示一个类及其字段；名称交给 OAK 与真实本体词汇对齐，不能匹配则保留未对齐状态。这里的 recursive 是递归遍历已有 schema，不是自动发明子类。OWL 导出让结果可交推理器检查，也不保证模型提出的业务关系是真的。— [官方 README](https://github.com/monarch-initiative/ontogpt)，[自定义 schema](https://github.com/monarch-initiative/ontogpt/blob/main/docs/custom.md)
- **DeepOnto。** 提供 OWL 本体处理、推理以及 BERTMap 本体对齐、BERTSubs 上下位推断等工具。它说明已有词汇复用、跨本体匹配、逻辑修复是独立工程模块，不是把近义标签聚在一起即可完成。— [官方文档](https://krr-oxford.github.io/DeepOnto/)，[对齐教程](https://krr-oxford.github.io/DeepOnto/bertmap/)

### Inferences

建议先复用稳定的项目/任务/决策/证据概念，再由模型提出类型或关系增量，并检查候选子类是否真满足父类定义、关系方向和基数是否合适、旧实例是否应迁移。形式一致性验证只能发现定义体系里的逻辑冲突，无法单独证明会话事实、因果判断或分类粒度有用。对本项目，自动生成本体最终应服务“为当前任务找对上下文”，按下游任务收益控制细分，避免为了建树而不断增加类别。

### Gaps

这些方法不提供已验证的跨宿主逐轮捕获、长期身份稳定、无人干预拆类合类迁移完整方案；仍需用合成例子和反例检验。由另一模型按任务组装上下文的运行时与训练研究，另见 [任务条件化上下文组装](<任务条件化上下文组装-论文与运行时-2026-10-31-公开整理版.md>)。
