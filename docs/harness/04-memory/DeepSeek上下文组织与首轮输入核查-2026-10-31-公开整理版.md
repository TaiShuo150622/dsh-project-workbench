## 文章对自主组织和执行上下文提出了什么

### Takeaway

文章把多任务组织、事件准入、上下文按需展开与异步执行结合起来，核心目标是减少人管理会话的负担。用户现在提出的“独立模型先从记忆组织好任务相关上下文，再交给执行模型”，是可以沿这条思路发展的额外职责；官方公开原型并没有完整实现这层语义准备。

### Cited Findings

- 已读同一篇文章的完整署名转载正文，第 1—9 节及致谢；来源覆盖和 B 站原页未核实的边界见同目录 `bilibili_superagent.md`。原始入口：[公众号](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)；实际全文入口：[署名转载](https://www.chaincatcher.com/article/2300676)、[补核转载](https://www.uied.cn/posts/922127)。
- 全文形成的组织链条是：全局协调与任务执行分开；事件先过滤再路由，确定归属后直通；信息按引用逐步展开；后台任务与前台沟通解耦；状态持久化并监控进展。第 3.4 节的提前行动是提前尝试工作，第 3.3 节的缓存比喻是内容内联与外置；两者都没有给出独立模型预编译完整 Worker 上下文的算法。来源：[原文第 2—6 节](https://www.chaincatcher.com/article/2300676)。
- 第 7 节实验主要考察合成消息负载下的任务调度、订阅直通与 Router 批处理。其 Prefill 讨论是把积压 Trigger 合并进一次 Router 请求，摊薄每个路由决定的耗时；不是验证执行模型首轮输入变短或首 token 延迟下降。第 8.1 节仍将长期记忆视为开放问题。来源：[原文第 7—8 节](https://www.uied.cn/posts/922127)。

### Inferences

- 文章的可复用原则是让系统主动安排“什么信息在什么时候到达哪个执行上下文”，而不要求人手动维持多个会话。
- 本项目可以把组织对象从 Trigger、Thread、Ticket 进一步扩展为需求、约束、历史决定、失败条件、代码实体和证据，从而形成任务驱动的 Context Builder。这个扩展应明确为本项目设计，而非原文已有结论。
- 提前整理背景、预热检索结果与预热模型 KV cache 是三件不同的事。文章的提前行动不能作为后两者已实现或已测有效的证据。

### Gaps

- 文章没有报告记忆选取准确率、上下文压缩忠实度、执行首轮 Prefill 时间、首 token 时间或任务正确率的受控对比。
- 对 B 站反爬不再重复尝试；本次沿已确认的文章与官方源代码深入。

## 公开原型实际上由谁在何时组装什么

### Takeaway

公开原型采用“模型判断路由与准入，程序组装有界任务卡，执行模型按需展开”的结构。它有相当完整的可读引用、权限、版本和投递语义，但没有一个独立记忆模型在 Worker 首轮前为任务做跨历史的语义选材与证据编排。

几个影响方案判断的具体实现点：

- 首条 assignment 的内联上限为 1,500 字符、trigger 为 600 字符，同批其他 trigger 为 160 字符预览。实现直接 `slice()`，并非模型语义压缩；上限是 JavaScript 字符尺度，不是 tokenizer token 预算。来源：[src/executor/dsh.ts 112—130](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L112)。
- 关联 Ticket 列表最多 8 个，活动项优先；Ticket 展开时给出首批 assignment/input、原 trigger、Thread 和更多读取地址。这是显式对象图，所读代码路径未做 embedding 检索或自动本体推理。来源：[src/app/cards.ts 59—95](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/cards.ts#L59)。
- Worker 不能读取其他 Ticket；在共享 Thread 的结果中也隐藏其他 Ticket 与 Decision 信息。读取有来源、归属和跟随关系约束。来源：[src/app/resources.ts 93—148](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/resources.ts#L93)。
- 内存 `TextCache` 是按字符总量限制的 LRU，服务分页快照和飞书链接，重启丢失；这不是模型注意力 KV cache。来源：[src/app/cache.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/cache.ts)。

### Inferences

- 确定性编译器与独立模型不是二选一。模型可以负责找候选证据、识别当前任务所需约束及缺口；程序负责验证证据权限、预算、版本与来源，并把材料稳定地编译进输入。
- 原型“只附短预览、让 Worker 补读”降低了初始输入体积，但可能增加执行模型后续读取轮次。本文讨论由便宜模型提前承担这些选材工作，以避免昂贵 Worker 重复寻找背景。两种策略需要在同一任务集比较，不能仅看首轮字符数。
- 现有原型的 `complete: true` 只用于 Router 的 system-prompt section；Worker 在宿主 prompt 与仓库指令上追加自己的部分。实际首轮还包含宿主、仓库规则、工具定义等，不能把任务卡长度冒充整个首轮长度。
- 相关性不能突破可读范围。若 Context Builder 能看更多历史，它交给 Worker 的材料仍需逐项按 Worker 的权限过滤，不能用摘要绕过原型的资源隔离。

### Gaps

- 未做完整仓库形式证明；“未实现独立语义选材”以已追踪的候选生成、准入、Worker launch、system prompt、资源读取实际主路径为依据。
- 未运行官方测试，以上测试内容是代码可见契约，不是本次通过结果。

## 对本项目新增上下文准备层意味着什么

### Takeaway

建议把智能 Record 定位为持续更新的证据和语义索引，把新的 Context Builder 定位为执行前的任务相关选材者。最终交给执行模型的是带证据、时效、冲突和续读入口的有限输入，而非一份更长的历史摘要。

### Cited Findings

- 可继承的官方基础分别是：对象 ID 可继续读取（[资源接口](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/resources.ts#L210)）；组装逻辑与提示词版本分离（[prompt 编译](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/prompts.ts#L98)）；事件可去重后直通（[入站路由](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/intake.ts#L19)）；后台工作结束不等于首个 turn 结束（[执行 hooks](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L476)）。

### Inferences

以下为本项目建议，不是对 DeepSeek 已实现能力的转述：

1. **记录阶段**：每轮把原始事件持久化；抽取实体、约束、决定、失败条件与出处，形成可重建的语义索引。保留决定何时失效、适用哪个分支/环境及后来被什么纠正。
2. **任务到达阶段**：独立模型读取当前目标，拆出“完成这项任务必须知道什么”，通过关键词、语义检索和本体关系取候选。这里的输出是证据选材计划，不应擅自扩大用户任务或创建新授权。
3. **执行前阶段**：独立模型选出最小充分材料，程序检查权限、时效、证据存在、相互冲突及 token 预算，冻结一版 Context Manifest。完整当前请求和适用指令应直接进入；不能只保留小模型对它们的改写。
4. **交给执行模型**：稳定规则放前缀，动态任务材料在后面；每项事实带原始出处，推断单列，重要否决条件与未解决冲突明确呈现。省略材料保留可访问引用，不要求执行者只能相信打包内容。
5. **执行期间**：只补充新的相关变化；缺失内容仍允许执行模型自行检索，并把补读反馈给 Context Builder，评估它前置选材漏掉了什么。

“自动搭建本体”和“首轮高质量 Context”之间还需要一个选择目标：本体可以很细，但不能把所有相邻节点都放进去。优先覆盖当前动作的前置条件、有效约束、最新决定和适用的失败经验，避免仅因词语相似就加入旧案例。

首轮便宜与整体更好必须分别量：

- 执行模型首轮：实际输入 token、未缓存输入 token、缓存命中 token、Prefill 耗时（若服务暴露）、TTFT。
- 准备层：检索与模型耗时、调用成本、缓存命中、过期重建率。
- 整体：从用户请求到可用结果的耗时、所有模型和检索总成本、任务成功率、关键约束遗漏、过期/错误记忆引入、执行模型补读次数。
- `用户可见等待 = 准备层等待 + 执行首响应等待`，若两段可并行才扣除重叠部分。把成本移到另一个模型不自动等于省钱；Worker 输入少也不自动等于任务更准确。
- 比较至少覆盖：现有执行模型自行查找、固定规则检索、独立模型选材、独立模型选材加本体关系。保持同任务、同执行模型和相同工具权限，允许各方案暴露自己的选材开销；数据必须按时间和任务隔离，不能用未来已完成的结果准备历史测试任务。

预热可以先做低风险、可复用的背景准备：对活跃任务建立证据候选和摘要缓存。缓存键应包含目标、数据/证据版本、工作树或提交、权限范围和组装版本；目标改变或证据更新时要失效，不能把猜到的下一项任务当作用户已下达的指令。是否预填充模型 KV cache 则是另一个依赖具体模型服务能力的工程问题，不能从应用层 `TextCache` 推导。

### Gaps

- 需要继续讨论 Context Builder 的任务边界、允许使用的模型与预算、证据包长度和执行失败后的反馈方式；这些都未被当前调研自动确定。
