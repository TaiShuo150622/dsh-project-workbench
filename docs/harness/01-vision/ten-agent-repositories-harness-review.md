# 十个 Agent 仓库核查与 Harness 借鉴分析

> **公开整理版**：基于原稿《十个 Agent 仓库核查与 Harness 借鉴分析》（源版本：0.1）。本次删去私有项目实例、公司项目专属内容及原始个人语料，未重新验证实验。源稿状态：reference；源版本编号保留，公开编辑不代表实现完成或新验证结果；章节与条目沿用源编号，删节后可能不连续。

**调研补充稿 v0.1｜核查时间：2026-10-28 UTC（本地为 10 月 27 日）**

本文对应 B 站文章[《10 个开源 Agent 构建框架》](https://www.bilibili.com/opus/1264078436551360516)。原稿调研时读取了文章正文，并另查各项目公开材料；本次未重新核验外部事实。

文章用于确认名单。本稿对能力和现状的判断另行核对了官方 README、文档、GitHub 元数据，以及 Agno 模板中的少量配置和评测说明。没有安装这些框架，也没有运行它们的模型调用、评测、服务或性能测试。下文的采用优先级和设计建议，是结合[我们的 Harness 讨论稿 v0.1](<harness-discussion-v0.1.md>)作出的判断。

## 1. 主要判断

这十个项目覆盖执行框架、长期状态、工作流编排、模型接入和网页采集等不同职责。对我们的目标，最值得先研究的是三组机制：

- **Agno：从运行证据、新版能力和代码问题生成改进任务，再通过评测改善行为。** 它与“新信息推动已有工作方式改变”的外循环最接近。
- **Letta：让记忆、技能和运行扩展具有持续状态与版本，并能生成动态工作流。** 当前版本的范围已经明显超过文章中“记忆层”的归类。
- **Pydantic AI：结构化契约、运行过程评价、能力组合和按需加载。** 它能为变更提案、实验结果和工具调用提供可检查的边界。

Microsoft Agent Framework 的恢复机制、LiteLLM 的成本记录，也能帮助我们把迁移成本和运行成本落到具体记录中。

**本次查看的官方资料中，尚未找到一套开箱即用的通用机制，完整比较“维持、小修、重构”的未来净价值、证据不确定性和实施时机，并同时落实我们要求的最低跟踪投入。** 已有项目能够提供大量基础机制；上述判断仍需要结合我们的目标、约束和真实结果来设计。

## 2. 十个项目的职责与借鉴点

| 项目 | 当前主要职责 | 对我们最值得借鉴的内容 | 采用时需要明确的边界 |
| --- | --- | --- | --- |
| [Agno](https://github.com/agno-agi/agno) | Agent、团队、工作流、持久运行及改进平台 | 运行证据驱动的改进任务；场景探索、修复和回归评价 | 改进循环的存在不等于已有通用的重构价值模型；部分模板评测只支持 agent/team。 |
| [CrewAI](https://github.com/crewAIInc/crewAI) | 角色协作与事件驱动 Flows | 把有状态的确定流程和局部自治研究组合起来 | 角色划分不能替代证据质量和责任边界；增加 agent 需要证明价值。 |
| [Pydantic AI](https://github.com/pydantic/pydantic-ai) | 类型化 AI SDK、Harness、Evals 和 Graph | 结构化提案；结果与过程评价；动态工具和能力加载 | 类型正确不代表事实正确；按旧路径打分可能阻碍合理重构。 |
| [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | 轻量 agent 执行、工具、委派、会话和 tracing | 明确执行循环；区分委派任务与移交控制；统一运行记录 | SDK 的 guardrails 不能自动实现我们的方向治理和最低复核义务。 |
| [Semantic Kernel](https://github.com/microsoft/semantic-kernel)／[Microsoft Agent Framework](https://github.com/microsoft/agent-framework) | 应用集成、多 agent 与图式工作流 | checkpoint、恢复、稳定执行器身份、中间件和可观测性 | 恢复旧执行与迁移到新结构需要分别处理。 |
| [Qwen-Agent](https://github.com/QwenLM/Qwen-Agent) | Qwen 相关工具调用、RAG、代码解释器与 MCP | 模型协议适配；工具注册与具体执行的分层 | 当前默认分支更新较久；新模型和接口兼容性需要实际验证。 |
| [Letta](https://github.com/letta-ai/letta)／[Letta Code](https://github.com/letta-ai/letta-code) | 有状态 harness、长期记忆、动态工作流和 mods | Git 版本化记忆与技能；生成候选流程；按事件扩展运行机制 | 可修改自身并不能证明改动有效；硬约束不能被普通自修改过程绕过。 |
| [n8n](https://github.com/n8n-io/n8n) | 应用连接、触发器、可视化自动化与 AI 节点 | 外部事件接入、到期复核、稳定动作流程 | 许可有用途限制；完成一个流程不等于正确选择了这个流程。 |
| [LiteLLM](https://github.com/BerriAI/litellm) | 多模型网关、路由、成本与调用管理 | 按任务和实验记录模型成本、重试与回退 | API 成本只是总成本的一部分；回退换模型会影响实验可比性。 |
| [Oxylabs Web API MCP](https://github.com/oxylabs/web-api-mcp) | 商业网页 API 的 MCP 接入 | 搜索、读取、异步结果、长结果分块和采集失败表达 | MCP 服务可自托管，采集能力依赖厂商 API；获取内容不等于验证内容。 |

表中的借鉴建议是我们的设计推论；各项目的具体事实与来源在下面逐项说明。

## 3. 逐项核查

### 3.1 Agno：优先研究它的改进外循环

**核实到的能力。** 当前 README 将平台分为构建、持久运行和改进三个部分，明确提到通过 traces、评测和历史会话发现问题，由编码 agent 进行场景探索、实现改动并保留回归测试。运行层包括 API/MCP、调度、恢复和人工介入等机制。[Agno README](https://github.com/agno-agi/agno/blob/main/README.md)

更具体的参考在官方 Railway 模板的 `app/company.py`：维护例程读取当前代码和固定版本之后的 Agno releases，提出改进任务；任务需要来源、修改理由和验证方式，并避免重复提案。配置设为 `auto_accept=False`。这是静态配置证据，不代表我们验证了这个例程已经成功运行。[维护例程源码](https://github.com/agno-agi/agentos-railway/blob/main/app/company.py)

模板的 `eval-and-improve` 区分修复已知失败和探索新场景：先分类问题，再做针对性改动，使用新变体与已有回归案例检查效果。其说明也明确区分环境故障、模型行为和评价器波动。[评测与改进说明](https://github.com/agno-agi/agentos-railway/blob/main/.agents/skills/eval-and-improve/SKILL.md)

**我们可以借鉴。** 把“搜到新能力”接到一个持续的改进提案队列；每份提案关联证据、受影响工作流、预期效果和验证任务。执行当前任务与评估如何改进任务方式，可以采用不同的状态和节奏。

**需要补充。** 提案还应比较保持现状、最佳可行小修和重构的价值，计算未来使用量、迁移与重新验证成本，并决定实施时机。当前所读模板的 `Case` 评测目标是原生 agent/team，不能直接把整个 workflow 当作该接口的评测目标。它模拟的是用户请求，工具和数据库可能真实执行；不能直接等同于隔离的模拟环境。[评测目标与执行边界](https://github.com/agno-agi/agentos-railway/blob/main/.agents/skills/create-evals/SKILL.md)

### 3.2 CrewAI：借鉴 Flows 与局部自治的组合

**核实到的能力。** Crews 用于角色协作，Flows 提供事件驱动的流程控制，并能组合单次 LLM 调用和 crew。官方同时区分开源框架与商业控制平台。[CrewAI README](https://github.com/crewAIInc/crewAI/blob/main/README.md)

**我们可以借鉴。** 将证据接收、状态更新、评价提交、版本发布等有明确约束的步骤放在可检查的流程里；把生成备选方案、寻找反证等需要探索的工作交给局部 agent。流程应显式携带当前证据、候选状态、预算与复核期限。

**需要补充。** 给 agent 起不同角色名称不会自动产生独立证据。多个 agent 读取同一转载源，也不能算交叉验证。角色数量和讨论轮次应由实际质量、成本和新增信息量评价。

**当前判断。** 值得借鉴组合方式；是否引入整个框架，需要证明它能补足现有 harness 的具体缺口。

### 3.3 Pydantic AI：把提案、过程与结果做成可检查对象

**核实到的能力。** 当前项目包括类型化 agent、可组合的 Harness 能力、Pydantic Evals、Pydantic Graph 和持久执行集成。Harness 涵盖记忆、规划、子 agent、上下文管理等能力。[Pydantic AI README](https://github.com/pydantic/pydantic-ai/blob/main/README.md)

Evals 可以检查工具选择、调用顺序、参数和调用预算，并利用 trace 观察嵌套 agent 的过程；这些评价与最终回答的评价可以组合。[Agentic Evaluators](https://pydantic.dev/docs/ai/evals/evaluators/agentic/)

动态工具方面，`prepare` 可以在每一步调整或隐藏定义；Tool Search 支持按需发现延迟加载的工具，能力包也能按需披露。不同模型供应商的实现路径有所区别。[动态工具与 Tool Search](https://pydantic.dev/docs/ai/tools-toolsets/tools-advanced/)，[Capabilities](https://pydantic.dev/docs/ai/capabilities/overview/)

**我们可以借鉴。** 将证据记录、变更提案、成本估计、实验结果、迁移计划和复核义务做成明确契约；同时检查结果质量、必要执行约束和资源使用。它也直接回应了我们对“开头暴露工具还是过程中加入”的讨论。

**需要补充。** schema 校验只能保证结构与部分约束。评价流程重构时，不能把“完全重复旧调用路径”当作总体正确性标准；路径改变正是重构的内容。过程评价适合检查必要顺序和不可绕过的条件，方案优劣仍需看结果、成本与风险。

**当前判断。** 评价层和数据契约层的高优先级参考；若采用 Python 实现领域实验，可以进一步评估直接复用相关包。对现有其他语言的 harness，也可以先借鉴其接口与评价思想。

### 3.4 OpenAI Agents SDK：保留清楚的执行与委派语义

**核实到的能力。** SDK 提供 agents、函数/MCP 等工具、agents-as-tools、handoffs、guardrails、会话管理与 tracing；当前也包含长任务 sandbox agent 等入口。官方定位支持多个模型供应商。[OpenAI Agents SDK README](https://github.com/openai/openai-agents-python/blob/main/README.md)

**我们可以借鉴。** 让“把一项研究任务交给子 agent 并收回结果”与“把对话控制权交给另一个 agent”具有不同语义。对于我们的系统，核心决策记录应能够串起主循环、工具调用和委派结果，而不是只保存最后摘要。

**需要补充。** 通用 guardrails 是实现校验的接口，不会自动知道我们的业务规则。只有人可以完全暂停方向、必须按期复核、重要变更必须满足什么约束，都需要显式实现。模型和工具版本也要进入实验记录。

**当前判断。** 适合作为轻量执行循环和清晰接口的参考。是否替换现有执行底座，应与现有能力及迁移成本比较。

### 3.5 Semantic Kernel／Microsoft Agent Framework：恢复与结构迁移要分开

**核实到的变化。** Semantic Kernel 当前 README 明确将 Microsoft Agent Framework 列为继任框架，并提供迁移入口。新框架提供图式编排、中间件、checkpoint、流式事件和可观测性等机制。[Semantic Kernel 迁移声明](https://github.com/microsoft/semantic-kernel/blob/main/README.md)，[Microsoft Agent Framework](https://github.com/microsoft/agent-framework)

官方 checkpoint 文档明确要求：恢复后的工作流要保留创建 checkpoint 时的拓扑与执行器身份；稳定 ID 是兼容恢复的重要条件。[Checkpoint 与恢复条件](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)

**我们可以借鉴。** 每次运行绑定工作流版本、执行器身份、输入和状态格式。在提出重构时，显式列出已有任务能否继续使用旧版本、哪些状态需要转换、哪些结果需要重新验证。

**需要补充。** “有 checkpoint”并不能直接推出“旧任务能在新架构上继续跑”。迁移兼容性检查和状态转换，本身就是重构成本与采用时机的一部分。这为讨论稿中的迁移成本提供了可落实的检查项。

**当前判断。** 执行状态、恢复和版本边界的高价值参考；无需为了学习这些机制先迁移整个项目。

### 3.6 Qwen-Agent：模型协议适配值得看，维护状态要单独判断

**核实到的能力。** 项目提供工具调用、RAG、代码解释器、MCP 及模型配置等示例，README 也介绍了 Qwen Chat 的使用背景。[Qwen-Agent README](https://github.com/QwenLM/Qwen-Agent/blob/main/README.md)

本次 GitHub API 核查显示，默认分支最新提交时间为 **2026-03-04**，最新公开发行版为 **v0.0.26，2025-05-29**。这支持文章对更新间隔的提醒，但不能据此断言项目已废弃或所有 issue 都无人处理。[该次提交](https://github.com/QwenLM/Qwen-Agent/commit/31a4d36d123688581a9e9744427272b33ce940e0)，[发行版](https://github.com/QwenLM/Qwen-Agent/releases/tag/v0.0.26)

**我们可以借鉴。** 区分模型的工具调用格式、模型返回内容的解析、工具 schema 和真实执行入口。供应商接口看起来兼容，并不意味着工具调用行为、上下文组织和模型能力完全相同。

**当前判断。** 在确实要接入 Qwen 或本地模型时深入验证。通用工作流改进层可以保持独立，避免绑在某个模型家族上。

### 3.7 Letta：从记忆层扩展到可演化的有状态 harness

**核实到的变化。** 旧 `letta-ai/letta` README 已指向 `letta-ai/letta-code`；历史 V1 API server 位于归档分支。当前源码包含 harness、终端界面、App Server 和渠道接入。[旧仓库的迁移说明](https://github.com/letta-ai/letta/blob/main/README.md)

当前版本有三组与我们直接相关的机制：

1. **MemFS**：使用 Git 管理记忆与技能；常用内容进入上下文，较深资料按需读取，并保留修改历史。[MemFS](https://docs.letta.com/concepts/memfs)
2. **Dynamic Workflows**：生成工作流脚本，组织多阶段、并行和迭代任务；结果通过脚本在阶段间传递。[动态工作流](https://docs.letta.com/configuration/workflows)
3. **Mods**：扩展命令、工具、事件与权限处理；可按相关性提供工具，并重新加载扩展。官方明确 mods 是与进程共享访问能力的可信代码。[Mods](https://docs.letta.com/configuration/mods)

**我们可以借鉴。** 将假设、方法、技能和候选流程变成可追踪的版本，允许系统提出结构不同的新流程，再把候选送入独立评价。工作结束后沉淀的能力可以是记忆更新、skill、工作流或可执行扩展，各自有不同的发布与验证要求。

**需要补充。** Git 记录改变，不判断改变是否正确。可编辑记忆应引用独立保留的原始证据；自我修改能力也不能顺带修改评价底线和方向暂停权限。动态生成一个迁移计划或让多个评价 agent 打分，仍需接受真实约束和结果验证。

**当前判断。** 与 Agno 同列优先研究对象；尤其值得研究长期状态、能力沉淀和候选流程生成，而不是只按“向量记忆组件”理解它。

### 3.8 n8n：用于接入与稳定动作流程

**核实到的能力。** n8n 提供可视化自动化、应用集成、代码扩展和 AI 相关能力。[n8n README](https://github.com/n8n-io/n8n/blob/master/README.md)

其根许可对常规部分使用 Sustainable Use License，`.ee` 企业部分另有授权。因此不能把整个项目按 MIT／Apache 类许可理解；具体使用方式需与许可范围核对。[n8n 许可](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)

**我们可以借鉴。** 将订阅源更新、webhook、复核到期和已成熟的归档动作接入主循环。对于稳定执行的流程，可以采用明确节点和失败分支，减少模型反复规划相同动作。

**需要补充。** “复核任务被触发”不等于“复核已经完成”。我们的最低投入要求还需要完成凭据、截止时间和逾期处理；负责决定是否改变工作流的逻辑也应单独可评价。

**当前判断。** 连接源和外部应用较多时有价值；首版连接很少时，简单适配器可能已经足够。

### 3.9 LiteLLM：用真实调用数据支撑成本比较

**核实到的能力。** LiteLLM 提供 SDK 和网关形式的模型接入、重试／回退、成本跟踪与调用管理。当前 README 也已有 MCP 接入和 harness 调用入口，因此它的表面能力比“转换模型 API 格式”更广。[LiteLLM README](https://github.com/BerriAI/litellm/blob/main/README.md)

根许可明确：`enterprise/` 目录采用其单独许可，其他符合根许可范围的内容采用 MIT。具体功能应查其所在目录。[LiteLLM 许可](https://github.com/BerriAI/litellm/blob/main/LICENSE)

**我们可以借鉴。** 为每个变更候选、实验和正式运行分配可关联的标识，记录模型、请求数、成本、延迟、重试和实际回退路径。把估计成本与实际成本持续对照，可逐渐校准重构提案中的运行成本。

**需要补充。** Token/API 支出只是一部分。人工审查、数据费用、返工、迁移与结果质量仍需另记；模型回退也要保留在记录里，否则效果变化可能被错误归因于工作流变更。

**当前判断。** 多模型或多实验并存时有较直接的复用价值；单一模型的小规模原型可以先保留可替换的计量接口。

### 3.10 Oxylabs Web API MCP：借鉴采集工具如何表达不完整结果

**核实到的能力。** 这是 Oxylabs 官方 Web API 的 MCP 服务，提供搜索、读取、异步结果查询和大结果分块等接口。README 还表达了内容过薄、可能需要 JS 渲染等状态，并提供调用限额。服务封装可自托管，实际网页获取依赖 Oxylabs API。[官方仓库与工具说明](https://github.com/oxylabs/web-api-mcp/blob/main/README.md)

**我们可以借鉴。** 数据工具应返回明确的完成、等待、失败和内容不足状态；大正文保留可追溯入口，模型按需读取。来源 URL、采集时间和内容版本应随结果进入证据记录。

**需要补充。** 采集失败、页面没有内容、事件没有发生，是不同结论。工具也不负责判断信源是否可靠或信息是否适用于当前决策。`readOnlyHint` 之类元数据不能代替运行时对真实执行与成本的判断。

**当前判断。** 适合作为网页采集适配器的设计参考。是否使用其付费服务，应依据我们实际遇到的采集缺口验证。

## 5. 对我们讨论稿的具体补充建议

下面是从本次调研推导出的设计建议，尚未修改原讨论稿的共识或选定实现底座。

### 5.1 把改进活动作为可持续跟踪的工作对象

借鉴 Agno，把一次新发现转成有证据、有对象的改进提案，而不是一段看完即止的建议。提案至少关联：触发证据、受影响假设、当前工作流版本、候选版本、实验记录、价值估计和复核条件。

它应该经历“待验证、试验中、证据更新、准备采用、已采用并待复核”等状态，并记录为什么发生状态变化。状态名和具体流程仍需结合实际场景确定。

### 5.2 分开候选生成、效果评价和迁移决定

Letta 能帮助生成和组合候选流程，Agno 提供运行证据驱动的改善方法，Pydantic 提供可检查的结果与过程评价。我们可以借鉴这些职责，但仍需独立表达采用判断：

\[
\text{候选相对基线的预期净价值}
=\text{未来结果改善}
-\text{新增实现、验证、迁移与运行成本}
\]

保持现状、小修和重构应在共同期限及一致评价标准下比较。证据不足时，选择下一项有决策价值的验证；收益成立时，再比较现在、模块边界和下一项目采用。

### 5.3 让评价支持合理改变执行路径

过程评价要检查必要条件，例如证据来源可追溯、不得用未来信息回放、重要动作满足权限和预算约束。它不应默认要求候选与旧工作流拥有相同的调用次数和路径。

最终结果评价则检查任务质量、可用性、可靠性、成本及后续实际表现。两者一起使用，才能区分“执行得符合约定”和“新工作流确实更好”。

### 5.4 把迁移兼容性纳入重构成本

每个运行记录绑定工作流、工具、模型和评价版本。变更提案应明确：

- 当前任务是否继续固定在旧版本。
- 新版本是否能读取旧状态，哪些字段或执行器需要转换。
- 哪些旧验证不再适用，需要重新验证。
- 哪个边界切换损失最小，发生问题如何回退。

这些检查项可以逐渐积累为实际工时和失败率，而不只依赖模型凭印象估价。

### 5.5 让能力发布与能力发现相连

Pydantic 的动态工具和能力披露，可作为会话中加载已有能力的参考；Letta 的 skills、工作流和 mods，可作为工作结束后沉淀能力的参考。

两者之间应有发布记录：候选能力经过验证，形成明确版本和适用条件，再进入可发现目录。工具可见、工具注册和执行权限仍然分开。

### 5.6 保留不随普通自修改而改变的要求

最低跟踪投入、周期复核和只有人可以完全暂停方向，仍由外部执行规则和方向状态记录落实。自我改进过程可以提出调整建议，但不能把这些义务从普通记忆或提示中删除后视为规则已经改变。

可以学习记忆和运行扩展如何版本化，同时保留独立的证据与决策历史。可恢复、可追踪与改得正确，是需要分别验证的性质。

## 6. 建议的阅读与验证顺序

1. **Agno 的维护例程与评测改进流程**：先研究外部新能力怎样变成改进任务，失败怎样被分类，修改怎样接受回归检查。
2. **Letta 的 MemFS、动态工作流与 mods**：研究长期状态和新能力如何保存、更新与暴露，并明确哪些权限需要放在自修改范围之外。
3. **Pydantic 的 Evals、动态工具与能力组合**：为提案、实验及过程约束设计可检查的接口。
4. **Microsoft Agent Framework 的 checkpoint 条件**：将运行恢复与结构迁移分开，定义版本兼容性。
5. **LiteLLM 的成本与调用记录**：在多模型或实验增多时接入实测成本。

CrewAI、OpenAI Agents SDK、Qwen-Agent、n8n 和 Oxylabs 可以按具体缺口继续深入。这是阅读与验证顺序，不意味着要把这些框架全部接入同一个系统。

本次结果支持继续完善现有讨论稿；还不足以决定整体迁移到某个框架。
