版本与范围

这套工程最先可以提供给其他作者的东西，是一组能解释失败的工作契约和可复查场景。 工作台、Record、DAG、远程执行分别实现其中一部分；通过相同场景，才能知道换宿主后哪些含义保持，哪些能力缺失。

  • 版本：v0.1.1，七小时研究中的适配契约修订稿；后续修改按补丁号递增。
  • 主线：能力匹配 → 效果契约 → 恢复 → 行为场景 → 贯穿演示 → 实现映射。
  • 状态标记：条件模型已核；真实适配器场景待验证；接口为提案。

本稿为研究提案。已有 Python 有限模型、TLA+ 检查及两份 Lean 一般证明，原始结果另附；本稿的真实适配器场景尚未运行，没有修改 DSH、Codex、Claude、Qwen 或现有 Record 产品。下文的接口名称是讨论词汇，不是已冻结的 SDK。

总体架构：能力声明落实到一次操作

能力声明至少限定主体、目标、操作、版本与配置，调度器按任务要求逐项匹配。 一个宿主支持幂等调用，不意味着它所有工具都幂等；一种存储的写入围栏，也不自动约束浏览器或远端服务器。

设任务要求的保证为 R，适配器在作用域 σ 下已有证据的保证为 C(σ)。只有 R 中每个条件都被 C(σ) 满足，才可采用该执行路径。这里的“满足”需要检查条件、期限和对象匹配，不能只做能力名称的字符串包含。

声明项必须说明不足时的可用做法
持久提交哪些事件/收据原子提交，何时向调用者确认暂态进度明确标注，故障后重新核实
目标幂等业务键命名空间、参数一致性、并发行为、保留期限、实际覆盖的效果unknown 后保留占位；改为权威对账或人工决定
目标 fencingtoken 的权威来源、单调范围、目标校验点、哪些写入受限只承诺本地准入或存储写入围栏
取消和终止取消信号、函数结束、进程及子进程结束、外部效果解决分别可证到哪里分层显示，未证实部分保持未解决
授权actor/代表关系、Grant 链、准入时或提交时有效；最终资源/参数与批准如何绑定提案模式、等待授权或采用更窄操作
上下文当前策略独立传入、实际材料 manifest、义务缺口、访问范围显示未覆盖项，不标为完整上下文
费用后验计量、阈值准入、未结算负担上界或目标强制配额采用软预算并说明范围，不许诺硬上限
读回目标权威、观察主体/用途/范围、陈旧性、时钟误差与未找到含义未找到仅作观察，不自动当作未生效

“尚未核实”“明确不支持”“在该配置下通过”是三个不同结果。没有某项能力不等于宿主不合格；要求那项能力的任务才不能选择该路径。

2. 一份幂等契约需要覆盖什么

稳定业务身份、目标原子去重和足够长的去重保留期必须同时成立，才能使用相应的重复效果保证。 相同参数不必是相同业务意图；同一业务意图也不能在每次尝试时换新键。

条款应明确的规则最小反例
身份与范围谁分配 businessIntentId；目标/租户/操作如何命名空间化两个独立的相同金额动作被错误合并
参数绑定同键不同参数拒绝或明确处理，最终有效参数在绑定范围内审批后包装器换目标，同键却执行新动作
原子效果去重决定与覆盖效果具有什么原子或可恢复关系，提交与恢复点在哪里先写效果再写去重，中间崩溃后再次执行
并发重复同键并发由目标收敛为一个效果，结果如何读回两次先查“无记录”后各执行一次
保留期限保留起算点、发送/到达/提交期限、最大迟到界或目标过期拒绝；旧未决请求如何处理到期前已发送的请求，到期删除 key 后才提交
效果覆盖一次工具内部哪些子操作被去重，哪些另有身份主记录去重了，通知或后台任务重复

第一份 TLA+ 样例固定为一个不可变业务意图、至多三条请求、两个目标代际，目标去重集合不丢失；另一个期限模型固定两条请求及目标时钟 0…2。后者已找到“仅限制发送”及“目标仅在接收时检查期限”的重复提交反例，而提交点拒绝过期、去重保留至该期限的配置在有限域内通过。模型没有多个租户、参数碰撞或恶意目标；实际适配器仍需补齐相应契约。模型和回执

fencing 解决另一个问题：目标在提交时拒绝已经安装的较新代际之前的请求。同代际的重复请求仍可能重复生效；稳定幂等键也不保证旧执行者不会以新业务键发起其他效果。两者应分别声明，分别核查。

恢复流程应先保留仍可能发生作用的请求，再依据具体证据减少未知范围。 本地调用结束、远端进程结束、业务效果解决是三个独立观察。

4. 同一组行为场景怎样用于不同宿主

场景按所声称的保证选择，失败判断必须来自可观察事实。 某配置明确不支持硬预算时，只有相应硬上限断言标为 UNSUPPORTED；负担保留、结算等基础会计场景仍可运行。不能用“没有超支样本”换取硬保证通过。

5. 最小演示应该贯穿一个真实目标

首个演示只需一个公开或合成 Coding 任务，但必须跨过需求、执行、证据与验收四个边界。 不需要先做复杂的自主记忆系统，也不要求同时接五个宿主。

6. 从抽象事件到真实实现的精化表

实现验证首先找清楚每个抽象事件对应哪一个持久化或目标提交点。 如果找不到这个点，不能只用同名日志证明模型已经落地。

抽象事件实现必须指出观察到失败时如何报告
Reserve哪个事务同时检查条件并建立占位未接纳／已接纳但回执丢失／无法判定
DispatchIntent最后一次动态检查及其绑定版本；出站身份不把意图入库当目标已收到
TargetCommit目标端效果提交、去重与 fencing 的真实范围无法原子覆盖的子效果分开
ObservationAccepted来源认证、原始数据、解释器规则与接纳事件原始记录存在但业务证明不足

风险与开放问题

契约最容易失败在作用域被悄悄扩大、观察被当作真相，以及测试工具与被测规则共用同一个错误解释。 文档应把这些风险放在读者能找到的位置。

  • 同一名字在宿主中含义不同：run completed 可能只表示模型循环结束，不能直接映射为业务目标已验收。
  • 只在内核中加 fencing：旧执行者也许不能写当前数据库，却仍可调用外部目标。必须标出被隔离的资源。
  • 回执存在但材料丢失：持久日志中保存一个 URL，并不保证产物一直可读或历史一直可重放。
  • 测试检查器同源：两种算法共享语义解释器，只能证明算法层一致。应加入独立语义真值表、手工小反例或其他表达的交叉核查。
  • 模型和例子过窄：两动作、两代际的检查不会自动覆盖任意并发、动态参数和多租户范围。
  • 过早统一：首个真实场景尚未打通时，不先承诺所有宿主共享完整 schema 或所有目标使用同一验收强度。
  • 为首个适配器明确作用域、观察来源与尚未支持的保证。

待证命题与下一步

下一步应先做一条具体适配路径的证据闭环，再冻结公共协议。 H01–H03 提供可解释状态、持久化与真实效果读回；其他组件据此渐进增加。
