# DeepSeek Harness 作者登记文案方案 v0.1.0

2026-11-08 · 个人插件作者登记方向 · 供讨论，尚未提交

## 建议名称

**Project Workbench｜项目工作台**

定位：面向 DeepSeek Harness 的个人项目工作台，逐步探索远程执行、长期任务与小团队使用方式。

## 简介

我主要以个人插件作者身份，围绕 DeepSeek Harness 开发项目工作台，同时探索小团队的使用方式。希望把项目、会话、工作树和交付产物放到同一条工作路径中，让用户能查看任务依据、当前结果和待处理问题，再逐步衔接远程环境与跨会话的长期任务。计划让 Record 管理任务、证据与验收的关系，用 DAG 呈现依赖和变更影响，二者属于同一工程。目前已有项目工作台代码，以及尚未接入工作台运行入口的 Record S1 研究内核；可信入口、远程接续和完整交付闭环仍为分阶段计划。我关注断连、需求变化和执行者切换后，怎样有依据地继续工作、保留未知效果并如实呈现结果，也关注如何让使用者少做重复解释和状态核对。下一步准备先做一个可复核的小任务，确认边界和实际价值，再逐步扩展。

## 目前成果

**已有代码**

- 项目工作台已有项目与线程组织、原生会话及工作树衔接、基本状态和差异查看等代码。这里描述固定版本的实现范围；尚未据此完成全部宿主、远程和恢复组合的验收。
- Record S1 已有独立研究实现，覆盖普通 PR merge 窄域的任务状态、确定性重放、精确请求重送、同步内存接纳和版本绑定验收。在本轮冻结输入中，它尚未接入工作台运行入口，不能与现有线程的 phase/accept 操作混为同一套验收。

**本轮完成的研究与验证**

- 已形成并通过 Lean 检查的两类条件证明：DAG 局部重算与全量重算的等价，以及保守预算在任意有限合法轨迹上的安全界；有独立编译与审读记录。它们依赖明确的输入、成本上界和转移条件。
- 已运行有限状态模型，检查准入、未知效果、支持撤回、验收绑定、预算、期限和接纳确认等边界，并保留故意削弱条件后的反例。这些结果属于有限模型，不能代替真实宿主和外部目标的运行验证。
- 对固定 Record 代码完成了选定既有测试、派生探针和实现映射；对宿主可信入口进行了静态调用链核对，明确了历史绑定、角色映射及状态投影的后续接线责任。可信入口尚未实施或验收。

**仍在讨论的研究**

- C-08 已形成自主推进、终止、期限及责任交接的条件研究和小模型，尚待独立复核；当前只用它帮助提出问题和说明前提，不列为已经证明长期任务最终交付的成果。

## 尚未运行的七片计划

七片均为后续实施计划，按条件逐片决定是否推进，不作为七个已经完成的插件。

| 切片 | 计划交付 |
| --- | --- |
| I01 可信入口与正确投影 | 固定原历史和可信主体，区分历史收据、当前证据与验收状态；首片不接真实外部发送 |
| I02 选择、引用与影响查看 | 把有版本的对象引用带入讨论，在改动前查看明确依赖和需要复核的检查 |
| I03 尝试绑定与持久接纳 | 明确尝试、规格、历史代际及接纳/恢复之间的契约 |
| I04 真实交付与验收 | 为一个明确目标接通执行、权威读回和绑定版本验收，保留未知效果 |
| I05 Record 与调用前组装 | 连接轮后记录、后台整理和调用前材料选择，记录实际输入来源及缺口 |
| I06 一种远程模式与长任务续接 | 先选定一种远程运行模式，验证会话、环境、进程和未决工作在断连后的归属 |
| I07 有边界的经验复用 | 用固定任务和完整成本比较经验或工作方式变化，达到约定条件后再讨论采用 |

## 支持需求与合作想法

希望与上游围绕一个小型、可复核的插件接入案例协作：先确认推荐的插件接口、会话与历史生命周期、可信调用来源，再逐步验证结果读回、断连恢复和跨版本续接。最需要的是接口边界与兼容计划的说明、适合插件作者的最小示例，以及对失败和恢复路径的技术反馈。我可以提供个人项目的最小复现、带版本的讨论稿、反例模型和接入记录，并在约定范围内整理成社区可复用的案例。合作可从一次设计评审或一个明确问题开始，后续再讨论小团队试用、远程执行和长期任务支持。希望先把宿主与插件各自承担的责任、验收方式和支持范围说清，再共同决定实施顺序与投入。

## 拟向上游讨论的五个工程问题

1. **可信调用身份如何交给插件？** 针对标准 HTTP owner 通道和 agent 工具通道，插件应从哪个受支持接口取得可信主体或权限域，并区分用户、agent 与宿主事件？能否提供把调用来源、原历史和命令身份绑定起来的最小示例？

2. **“消息已接纳”对应哪一层确认？** 插件何时可以把返回值理解为重启后仍可核对的接纳？同一消息 ID 重试遇到内存命中或 flush 出错时，推荐通过哪些确认或查询路径区分临时可见与可恢复记录？

3. **远程续接有哪些稳定身份和生命周期事件？** 会话恢复、宿主重启、远端环境重建时，哪些 ID、代际和状态事件可以作为插件契约？插件怎样保持任务尝试与执行环境的归属，避免断线恢复时把旧 prompt 或工具动作误当成新工作重发？

4. **长期任务到界后怎样收尾并交接责任？** 对已发未决、取消中或接近预算/期限的任务，宿主能提供哪些可核对的执行、费用及效果观察？停止新增工作之后，结果收集、对账与责任交接有哪些明确支持的通道和权限约定，哪些需要具体目标适配器承担？

5. **插件与历史状态的兼容边界如何约定？** 对项目状态、Record/DAG 引用和未决任务，升级时推荐采用什么版本绑定及迁移方式？是否可以先明确最小受支持版本范围、迁移示例，以及旧版停止支持时如何保存查询和接管未决事项的能力？

以上问题来自已读固定版本及研究设计，拟用于确认推荐契约与接入方式。具体代码基线、来源范围和措辞边界保留在配套依据文件中；本稿仅表达合作意向，登记材料当前未发出。
