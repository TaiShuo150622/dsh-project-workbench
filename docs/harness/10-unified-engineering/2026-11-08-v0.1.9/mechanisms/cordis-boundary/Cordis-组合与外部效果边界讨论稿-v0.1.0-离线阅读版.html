版本与范围

Cordis 可作为统一 Harness 的局部组件生命周期基础；远端动作是否发生、发送者是否停止、结果是否仍有效，需要额外的动作证据契约，不能由插件卸载状态推导。

  • 版本：v0.1.0，定向阅读 Cordis 原论文相关定义与证明，并核对 DSH 固定源码；首次整理。后续修改按补丁号递增。
  • 主线：论文前提 → 固定实现 → 正例与反例 → Record 适配契约。
  • 状态标记：原文核实、固定源码静态核实、本文推导、待验证提案分别标注。没有运行 DSH、第三方测试或真实远端动作。

研究对象是 Cordis 论文 v1（Yifan Shi、Wei Zhang、Tianyi Cui，2026-08-26）与 DSH 固定提交 fcc0ad4（2026-11-04）。后者 vendored Cordis 的 package version 是 4.1.0。版本固定不意味着论文与代码已经完成精化证明。

阅读覆盖见 READING_COVERAGE.md，逐来源信息见 sources.json。本稿不是 92 页全篇证明审计，也不声称发现了对论文主要定理的反例。

总体架构

统一 Harness 可以复用 Cordis 的所有权、依赖绑定与清理机制，再为越过组件边界的动作建立独立账本。

原文核实：§6.1 明确区分可独占恢复的位置与外部 emission；§5.1.1 明确 inverse 和 commutativity witnesses 不由运行时验证；§6.3 明确语言代理不构成恶意代码沙箱。论文，第 59、70–73 页

从左向右读：局部清理回执只是账本的一种输入；远端是否改变必须沿目标端观察这条线取得证据。

本文判断：无需把 Cordis 改造成通用分布式事务系统。更合适的接点是为工具和资源适配器声明“能撤销什么、怎样证明结束、哪些后果仍未知”，由 Record 保存这些证据的适用范围。补偿机制已有 Sagas 原论文，第 250、254–255 页 等先例；补偿可能失败、需要修复，也不会抹去其他观察者已经看过的中间结果。

并行清理的准确读法：论文 §5.1.3 本身也提到 fiber 级清理可并发；这不是本次发现的文档与实现冲突。需要严格顺序的清理应放在同一个显式 await 链或依赖关系中，不能凭顶层注册顺序推导全部完成顺序。DSH 生命周期教程第 94 行 也给出了这一限定。

统一 Harness 应补充的契约

Record 应把“生命周期事件”“发送者状态”“目标端效果证据”分开接入，再决定资源释放、结果适用性和是否可重试。

这是设计提案。现有 Record S1 README 只实现同步确定性模型：没有 DSH 拦截、真实认证、持久存储、跨进程锁或远端终止验证。不得用本稿将 S1 合成输入升级为宿主集成事实。

Algorithm 1 的局部记号疑点

第 59 页伪代码存在一处可复核的组合方向不一致；固定 DSH 同一 effect 组的实现并未照着这个顺序写。

核实方法：网页截图接口不可用后，使用原始 PDF 内存渲染该页局部并目视确认，未保存论文副本或图片。Algorithm 1 的第 6 行是 inverse ← value ∘ inverse；相邻文字将 f ∘ g 定义为先执行 g 再执行 f。按此约定，先得到 g1 后得到 g2 会得到 g2∘g1。原页

本文独立算术检查：令状态为实数，从 0 开始先 +1 再 ×2，最终为 2；对应逆为 −1 和 ÷2。LIFO 给出 (2÷2)−1=0，上述更新方向给出 (2−1)÷2=0.5。（数字是说明用假设。）Def. 18 及 L-Iter 的 g∘h 则按正确 LIFO 方向组成。

限定：这是一般局部 effect 构造的转写/记号问题，尚未向作者求证；若只考察完全可交换的逆，该差异不会显现。它不是 Thm. 68 的反例，也不是 DSH 的已复现 bug。固定 fiber.ts:433–447 使用 reverse，并在同组遇到异步清理后用 promise 链串联。总稿宜将此项放入待核对附注，不用它承载架构结论。

风险与开放问题

主要风险是把有条件的组合语义、固定代码的控制流和真实世界效果误写成同一层保证。

  • 证明范围：关键证明已读，不等于依赖闭包和全篇证明已经审计。
  • 接口假设：提供 disposer 只是语法；独占性、逆成立、返回值不受交错影响都要逐接口论证。
  • 回执含义：本地函数或清理链 settled 不能直接作为全局 senderTerminal 或 not_applied 证据。
  • 失败传播：需要识别清理日志中的失败与未完成项，不能只读取 fiber 最终状态。
  • 权限范围：注入约束与上下文 interception 应配合宿主隔离及执行点检查，不能充当恶意插件沙箱。

开放问题：

  • 哪些资源适配器能给出可靠的终止证明，哪些只能给“已请求停止”？
  • 目标端不支持幂等键或效果查询时，保留未知占用后的人工解锁条件是什么？
  • cleanup 失败是否需成为独立结构化事件，如何防止日志遗漏被误当成功？
  • 有序 hooks 哪些允许热卸载，哪些必须等待旧 dispatch 排空或检查 epoch？
