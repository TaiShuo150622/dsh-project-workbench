固定 DSH fcc0ad4 的 connection/index.ts:146–157 先 admit，再向 HTTP bridge 传入 Peer；rpc-host.ts:129–136 检查请求来源条件及已认证 browser/API Peer，:215–222 对精确 fetch 路由只放行 owner，之后 callback 只收到 Request。这是标准接入链的代码保证，不是本机运行回执。Host/Origin 检查自身不建立身份；BrowserAuth 另核签名、请求 audience 与有效期。owner 表示宿主权限域，不识别每位自然人，也不证明某次操作由人亲手确认。宿主入口；owner 门禁；精确路由

3. 不可混用的身份和版本

  • 主体：工具可取得注册 agent 对象；HTTP 精确路由可依固定宿主合同取得 owner 类别保证，但没有逐人 ID。未来映射应以 (identityAuthority, subject) 为域，再赋当前命令角色；正文中的 actor/role、sessionId、项目说明或模型声明都不是身份来源。
  • 目标：项目 UUID、线程 UUID、原生 sessionId 和线程 generation 分别服务项目成员/续接；没有一个现成字段可直接宣称是 Record 独立历史代际。将某人选中的 session 当其身份、将当前 UI 项目当旧请求归属，都会混淆作用域。
  • 请求：宿主 rpc.call 每次生成 rpcId，仅关联请求/响应；项目 dispatchKeys 仅按键返回旧线程。Record 则把 actor、payload、revision 等整体指纹纳入 requestId 去重。I01 要独立保留原命令 requestId，重试不能重取新 revision 或用新 UI 选择重包历史。RPC
  • 普通命令与验收：S1 普通 envelope 不含 streamId，必须在 apply 前由外层 HistoryBinding 选择并核对私有实例；不能仅靠内核 taskId/revision 去重。验收 token 含 streamId、任务/规格/完成/结果及可用性/验收版本，它是结果绑定数据，不是 bearer 身份凭据。创建命令无 expectedRevision，验收用 token，其他命令用 expectedRevision；两类均需可信 actor。内核

现有测试 USER/AGENT/VERIFIER 是固定常量；beginAttempt.payload.sessionId 在模型内只是经过格式校验的输入，真实会话归属仍归适配器。S1 的 replay、快照及 token 也不认证导入者。D01 不应把测试演员或历史 user/message 直接变成现在的授权；已核上游变更说明甚至保留“旧记录缺 principal 视作 owner”的兼容规则，这只是历史解释规则。

4. I01 需要改哪里、覆盖什么

建议新增 server/record-entry.js 与投影模块（文件名待实施冻结），私有保存 kernel 句柄及 history/宿主实例映射；顺序为可信通道→当前角色/读取范围→原历史与目标实例一致→命令白名单→原 requestId/revision/token→apply→分别返回历史收据与当前投影。普通命令必须在内核去重/查 task 前完成历史检查。

index.js 仅把选定通道接入该入口；可选 agent note 复用注册对象检查，不开放 agent 自报 user/verifier。client/app.js 新增独立状态块，意图创建时固定 history、对象和水位；生成的 client.js 后续应随正常构建更新。旧 Projects 的 accept、stop、report 与内部恢复继续明确标记旧语义；若选择将任一路径纳入 Record，必须同时处理上表的 HTTP、工具、事件、定时调度和原生会话回流，不能只有按钮走门禁。

首片建议白名单沿用 W07 的只读及 note/pause/cancel/acceptResult，具体角色仍待 D01 冻结；verifier 写入、真实 reserve/dispatch/效果发送关闭。演示所需初始化数据走明确合成夹具，不能展示成真实完成。持久 ACK、多进程互斥和实际外部对账留 I03/I04。

5. D01 备选与进入编码的前提

备选可借用的依据仍需决定/证明
