## 1. 决定、研究主张与历史观察分开

| 原有方向/表述 | 本轮处理 | 需要保留或补充的条件 |
| --- | --- | --- |
| 信息进入决策，并持续改善工作流 | 保留为总工程主线 | 当前任务循环和工作方式改进循环分别验收；不能只建设任务状态看板 |
| 工作流本身可小修、替换、重构，采用时机也应比较 | 补强为变更提案的明确对象 | 新能力也可触发；在共同未来期限下比较现在/试验后/下一模块/下一项目，计入验证、迁移和切换成本 |

## 2. “预测—检查—意外”的记录契约

这条方法线可以成为统一 Harness 的一个可替换策略模块，而不是每次简单编辑都必须走的高开销流程。

| 对象 | 需要绑定 | 形成时点 | 不能推导的事情 |
| --- | --- | --- | --- |
| Prediction | task/spec、attempt、输入版本、预计结果范围、检查规则版本、已知信息范围 | 相关检查第一次派发前，由可信流程提交 | 不能仅凭早时间戳证明作者从未见过相关结果 |
| CheckDefinition | 需求依据、判据、执行器版本、环境要求、负对照 | 检查前冻结，修订另成版本 | schema 合法不证明判据与真实目标一致 |
| CheckRun | checkDefinition、input artifact、环境、执行身份、完整输出引用 | 每次实际执行产生独立 run | 一次通过不覆盖其他环境/数据/产品版本 |
| Comparison | predictionId、checkRunId、偏差类型和大小 | 观察结果后 | 预测不准不等于代码错，结果很好也可能是检查器遗漏工作 |
| Diagnosis | 候选原因、支持/反驳证据、置信边界、建议措施 | 对偏差分析后，可以继续修订 | 分类文本不能直接授权破坏性回滚或修改检查标准 |
| ImprovementProposal | lesson、适用范围、候选模板/规则、对照与采纳标准 | 多个失败/收益证据积累后 | 一次经验不自动成为全局强制规则 |

顺序要求应表达为可信因果关系：`PredictionCommitted → CheckDispatched → CheckObserved`。若检查早已运行，后写预测不能冒充事前预测；可以标作事后解释。对反复运行同一任务，要记录作者/模型已看到的先前结果，避免把重复试验中的“预测正确”当独立泛化能力。

如果使用外部可运行终端，系统只能对它实际控制并记录的检查路径给出顺序保证。不能声称通过事件日志证明了人的主观无知，或证明模型训练中从未见过类似问题。

## 3. 意外处理如何进入有类型图

建议从“自动回滚依赖链”改成“沿已声明关系确定复核义务”。

| 新观察 | 首先改变什么 | 后继如何处理 |
| --- | --- | --- |
| 实现违反固定契约 | 当前尝试/产物的验收状态 | 保留原规格和检查器，形成修复尝试；复用未受影响证据 |
| 计划假设被反驳 | 指定假设的支持状态 | 查依赖该假设的证明路径；替代证据可继续支持，无法支持的任务重新规划 |
| 检查器不覆盖实际要求 | 检查规则的适用性与证据强度 | 旧输出仍在历史中，但不足以支持原结论；对受影响产物用新规则验证 |
| 环境与原假设不同 | 环境版本或适用域 | 区分环境修复与代码修复；重新运行前检查外部效果是否可安全重试 |
| 预测错误但产物符合目标 | 预测/理解模型的评价 | 不自动改正确产物；更新相关知识和下一次预测策略 |

这不要求首版实现通用自动诊断。先把诊断记录和依据接入已有工作台，让人能看清“改哪里、为什么、哪些旧结果还能用”，再评估自动化收益。

## 4. 如何衡量“减少审查”

旧稿用“机器未覆盖的自由度 × 判断所需上下文”帮助理解审查负担；本轮把它保留为启发，不当作已验证的定量定律。

建议同时记录四组结果：

1. 交付质量：预先定义的必需行为、严重错误、后续逃逸问题；不能只数通过检查的比例。
2. 人工成本：审查时间、额外查证次数、返工解释成本和最终接受所需交互。
3. 自动化成本：模型与工具费用、等待、宿主资源、维护模板和检查器的投入。
4. 适用范围：任务类型、规模、依赖版本、模板偏离和失败样本，避免把容易任务的收益外推到所有任务。

比较同一版本模型下的基础流程、加模板/生成器、加检查器、加事前预测、加记忆/检索等条件。可以先做小规模探索确定量表，再冻结留出任务与采纳规则。多组件同时改变时，不能把总收益归给其中一个组件；模型升级后需要重新消融。

## 5. 工具、主动性与工作流的历史提案

这些方向继续作为可替换策略，而不升格为统一内核的固定参数。

| 旧稿方向 | 本轮保留 | 本轮收窄或补充 |
| --- | --- | --- |
| 完整工具目录与少量可见工具分开 | 能力注册、描述、投影、调用契约和事件分层 | 3–8 个可见工具只是旧稿设计起点；现有 SDK 数量与延迟说明不证明普适最优，须保留发现失败与退出路径 |
| 工具使用经验难跨会话传递 | 经验进入带版本的说明、示例和可重用制品 | “每次对话从零、不能传递”过强；文件、技能和版本记忆已能传递，真正问题是适用性、选择与纠错 |
| 主动查资料后再问人 | 先读已有约束，继续无依赖的工作；会改变结果且无法自行核实的边界才提问 | 查询既可影响下一步，也可履行未来决策、审计、覆盖和监测义务；未知价值的探索需明确学习目标与预算，不要求事先知道答案 |
| Agent 与固定 Workflow 按任务选择 | 固定骨干、可复用计划、有限 Agent 与明确失败出口 | 旧稿 40 实例、5/10 点门槛、70% 诊断一致率是未运行提案，没有本轮功效或采纳依据 |
| 预测被证伪后重规划 | 保留预测—检查—偏差记录 | 环境、目标、输入与接口变化也可触发重规划，不必等待原预测先失败；维护原方向与当前执行策略分开 |
| 用成功案例比较成本 | 留下对交付质量与人工负担的关注 | 每成功交付成本的分子含同组失败、超时、构建、诊断、维护与人工；成功子集均值另列，不能替换整体分母 |
| 独立模型选材与后台本体 | 保留轮后摄入、低频整理、调用前选材三时序 | 水位尾部补最新约束；只有实际控制执行模型输入才能检验 prefill 假设，选材成本计入总成本 |
| 远程 A/B 与面板引用 | 保留每会话环境绑定、稳定实体选择和改动前影响检查 | 旧兼容结果不等于现行跨宿主验收；当前工作台 accept 的线程 phase 不等于 Record 验收令牌 |
