# 统一 Harness 架构与切片工作稿

2026-11-08 · 七小时研究内部工作稿 · 状态：机制与反例已交叉核查，仍是待实际贯穿验证的设计提案。

## 1. 核心取舍

建议采用一个小而明确的工作语义内核，连接可替换的执行宿主、记录/检索服务和工作台视图。工程范围可以很大，但没有必要先重写所有模型循环、终端、沙箱、浏览器和工作流引擎。真正需要统一的是：谁在做什么、基于哪个定义和证据、允许产生什么效果、怎样恢复、何时可以说已完成，以及错误判断如何传播。

这仍是一个完整 Harness 工程。项目工作台是人参与目标、执行和验收的入口；Record 负责跨轮次和跨宿主的状态及证据；DAG 是多种关系的表达和计算层；Coding 是首先落地这些契约的任务域；远程执行、浏览器和工具目录提供具体能力。

| 候选 | 优点 | 主要代价 | 本轮建议 |
| --- | --- | --- | --- |
| 在一个现成宿主中全部定制 | 首个流程接入快，原生 UI/工具可复用 | 核心语义易绑定宿主事件，换宿主时解释不同 | 可作为第一适配器，不把其字段直接当通用规范 |
| 从零建设完整代理平台 | 所有层可统一设计 | 需要同时承担模型循环、环境、工具、恢复和 UI 成本 | 先不作为默认路线，除非适配实验证明关键能力不可实现 |
| 小语义内核 + 明确适配契约 | 可复用现有宿主，跨框架验证同一行为 | 适配层必须如实暴露能力差异，不能抹平缺口 | 优先做一个真实最小闭环，再判断抽象是否合适 |

所谓“小”是权威写入面小，不是只能服务简单任务。权威内核不承载任意全文、不替模型推理、不直接管理所有 OS 进程；它维护任务、授权引用、动作占位、证据绑定和必要版本。大文件、全文记录、检索索引和图布局留在各自服务。

## 2. 五层职责与两条循环

| 层 | 负责 | 输入与输出 | 需要避免的越界 |
| --- | --- | --- | --- |
| 意图与工作契约 | 目标、范围、输入、验收、授权、预算、期限和改目标 | 人的要求 → 有版本工作契约 | 用模型自行扩大的目标代替人的实际授权 |
| 协调与权威状态 | 就绪计算、尝试分派、动作准入、证据接纳、取消/恢复与结算 | 命令与观察 → 事件、状态、收据 | 把任意工具文本当作有权状态变更 |
| 信息与证据 | 原始材料引用、结构化记录、来源、撤回、检索、上下文编译 | 资料与事件 → 可追溯材料及 manifest | 把摘要、嵌入相似度或记忆当事实证明 |
| 执行与环境 | 模型循环、工具、文件、沙箱、远程进程、目标端效果 | 被准入的动作/工作 → 观察与产物 | 用“调用结束”冒充“外部效果已经确认” |
| 人机工作台 | 项目入口、图、差异、证据、待决问题、资源与交付 | 只读投影 + 明确操作 → 人的决定 | 绿色状态掩盖当前可用性、争议或未结算效果 |

当前任务循环：意图 → 工作契约 → 选材 → 计划/执行 → 证据 → 验收/修正。

工作方式改进循环：多次执行的失败和成本 → 改进假设 → 候选流程/工具/提示 → 对照评估 → 采纳或拒绝 → 新版本。改进循环产生候选，不自行修改保护它的授权边界。候选部署仍受目标、预算与变更权限约束。

## 3. Record 的四种材料与写入权威

Record 是 Harness 的一部分，但它不是“所有文字存在同一个表里”。先区分权威状态和可修订知识，才能让记录真正帮助执行。

| 材料 | 例子 | 谁可以写 | 怎么纠错 | 用途 |
| --- | --- | --- | --- | --- |
| 工作与控制事件 | 规格修订、授权引用、派发、取消、验收决定 | 经认证与校验的命令处理器 | 追加纠正事件，保留历史 | 协调、恢复、审计 |
| 原始观察与产物引用 | 固定 SHA、工具返回、CI 产物、网页版本、带主体与用途的可用性观察 | 具有明确来源身份的适配器 | 撤回/替代观察；原件保留策略另定 | 核实具体判断 |
| 派生知识与经验 | 总结、抽取实体、教训、可复用步骤 | 模型或确定规则，但携带来源与方法 | 重算、合并、反驳、过期 | 检索、计划与改进 |
| 当前查询投影 | 看板、DAG、当前状态、上下文 | 从上面材料计算 | 清空重建或增量修正 | 人与模型的阅读入口 |

可追溯不等于无限保留。正文、凭据、个人数据和公司数据按各自权限与保留政策保存；公共研究只保留允许公开的材料。需要删除内容时，可以保留允许保留的最小审计元数据，但不能在未决定政策时承诺“所有历史永远不可删除”。跨项目记忆必须有显式共享范围。产物存在性与某主体的访问权分别记录；单个成员访问撤回只影响对应使用范围，不能直接把共享产物标成对所有人不可用。

建议的存储边界：结构化权威日志与当前投影；按内容摘要定位的大产物库；可重建的全文/向量/图索引；带访问策略的源材料存储。内容摘要用于定位与核对，不能代替访问控制或签名认证。

Record 的信息路径保留三个阶段：轮后摄入与增量抽取、后台按需整理、调用前独立选材和编译。它们不必对应三个常驻进程；知识水位之后的原始尾部应补齐未整理的最新限制。独立选材是待测策略，当前 S1 是工作状态内核，不能因为名称同为 Record 就声称记忆系统已实现。实际 prefill、缓存、执行质量与整理总成本须一起比较。

## 4. 最小公共工作契约

下表是待验证的公共语义，不是本轮决定的完整 JSON schema。只有第一条适配器和真实场景验收后，才冻结外部协议。

| 段 | 最少表达什么 | 关键校验 |
| --- | --- | --- |
| Identity | history、project、goal、task、specVersion、attempt | 不同历史的对象不能仅按相同本地 ID 互认 |
| Principal | identityAuthority、subject、actor、onBehalfOf、reviewer、Grant lineage | 认证通道解析身份；委派不超有效可委派范围 |
| Scope | 目标服务/对象、操作、效果、接收范围、delegableScope | 工具可见性不授予权力；跨服务凭据须匹配接收目标 |
| Inputs | 资料版本、接口假设、外部时点、披露范围与发布/转换依据 | 版本固定；检索、摘要及交付按本次消费者检查 |
| Outcomes | 目标类型、结果版本、材料化副本、按 q 的可用性、验收与证据 | 存在性、消费权、审计可达性和人的判断分别表达 |
| Dependencies | 有类型的前提及 AND/OR 关系 | 依赖哪个谓词、版本和有效期 |
| Effects | 逻辑动作、最终资源/参数摘要、executor scope、批准版本、恢复语义 | 业务意图身份稳定；效果相关改写后重判授权和必要审批 |
| Resources | 预算、在途负担、并发、期限、结算预留 | 不把预计成本当硬上界，不静默超授权 |
| Context | 必带义务、版本、水位、consumer、recipients、策略依据与缺口 | 当前权威策略独立传入，历史批准文字不能变成 Grant |
| Recovery | 可续接状态、环境要求、未知效果处理 | 哪些可重放、哪些只可对账、哪些要人决定 |

工作契约的版本向量不应无差别复制整个世界。只绑定动作或判断依赖的对象；用一个全局版本会让无关备注导致所有工作失效，用过短向量又会接受陈旧输入。第一版应选择可解释的少量字段，并通过反例验证充分性。

## 5. 四类目标采用不同验收

统一协议应允许不同验收强度，不能把全部工作强制转换成一条机械断言。

| 类型 | 示例 | 可机械核实的部分 | 人或统计评估负责的部分 |
| --- | --- | --- | --- |
| 精确效果 | 按指定 source SHA 合并某 PR | 目标身份、方法、merge SHA、父提交关系 | 为什么要合并、是否仍符合更大目标 |
| 工程改动 | 实现一个用户可操作的功能 | 构建、测试、指定交互、实际版本 | 需求解释、可用性、长期维护取舍 |
| 探索研究 | 比较方案并给出有依据的建议 | 来源存在、引用正确、覆盖指定问题、产物可取 | 论证是否充分、是否遗漏重要替代、决策价值 |
| 持续服务 | 跟踪一个方向或周期性检查 | 检查时点、观测证据、异常转移、预算 | 何时改变方向或彻底停止；观察窗口是否足够 |

探索任务可以完成一轮约定范围的研究，而不声称问题已被彻底解决。持续服务的“运行着”“本轮检查结束”“满足一段观察窗口”是三种状态。需要让工作台直接显示适用窗口与未覆盖范围。

## 6. 宿主适配器必须声明具体保证

一个统一调用接口并不意味着所有宿主能力相等。适配器要声明已验证的能力和缺口，让调度器选择可满足当前任务的组合。

| 能力 | 建议声明值 | 调度含义 |
| --- | --- | --- |
| 历史与恢复 | 无恢复 / 会话日志 / 可恢复工作状态 / 可重放事务步骤 | 不把“可续聊”当“旧工具不会重复” |
| 效果约束 | 分别声明入口准入、目标幂等、目标 fencing、事务边界及各自目标/操作作用域 | 这些是独立特征，不是可互换的安全等级；同一 fencing token 仍可能重复执行，幂等也不阻止旧执行者另造新键 |
| 取消 | 信号发出 / 执行者终止可证 / 效果已对账 | 只释放对应已经证明结束的负担 |
| 工具权限 | 提示约束 / 宿主拦截 / OS/目标强制 | 不能靠提示满足必须强制的边界 |
| 上下文 | 能插入材料 / 能列完整 manifest / 能绑定水位 | 缺少某能力时禁止声称材料完整 |
| 观察可信度 | 模型转述 / 原始工具记录 / 身份验证的目标读回 | 原始记录仍需判定业务充分性 |
| 资源 | 后验计量 / 阈值准入 / 保守预留 / 强制执行配额 | 任务硬预算与宿主能力匹配 |
| 环境生命周期 | 临时 / 可快照 / 可重连 / 可恢复工作进程 | 环境恢复和工作完成分别报告 |

身份/代表关系来源、Grant 委派链、工具限制强制点、审批共享范围、子代理工具面及数据返回接收范围，应作为独立特征声明。子代理可获得经明确配置的独立工具连接；工具列表不必是父列表的子集，授权仍须落在有效可委派 Grant 或新的显式 Grant 内。撤回一致性另标缓存/准入时/目标提交点，不以“支持权限”概括。

“未声明”与“不支持”分开；某宿主通过插件可以实现的能力，只有插件在指定版本验证后才标为已具备。不要根据一个 README 将完整产品判定为具备某种保证。每项声明都要带目标对象、操作类型、配置与版本，调度器检查任务需要的特征集合，而不是比较一个总安全分数。

初期优先支持当前 DSH 工作台宿主和一个结构明显不同的宿主。第二条适配器是检验抽象的手段，不能为了展示数量一次接五家。是否选择 Pi、Codex、Claude SDK 或其他候选，应由同一最小任务的能力差异和集成成本决定。

会话执行入口应区分本地、A 模式（本地 Agent 操作远端文件/命令）、B 模式（远端 Agent 执行）。文件、终端、审批、回调与会话身份共同绑定；UI 切换不隐式改变运行归属。模式选择与恢复保证是不同维度。

对于版本升级，额外声明历史解码、指定历史重放、未来调度接管、工具语义和动作身份、权限重检与旧效果责任交接。旧代码支持期、worker 退出与制品保留期分别决定，不把长期支持等同永久运行旧代码。[八项迁移契约](mechanisms/lifecycle-migration/contracts.json)是候选协议，六个故障场景尚未执行。

## 7. 一个动作经过哪些边界

1. 人或上层计划提出 TaskDefinition；经过目标范围与授权确认后形成固定版本。
2. 依赖服务读取所需证据和结果版本，按本次消费请求 q 计算就绪；不复用另一主体的 Usable，返回依据而非仅返回 true。
3. 上下文服务按主体范围准备来源和当前义务，编译 context manifest；不满足强制义务时显式报告。
4. 执行宿主生成候选动作。适配器完成效果相关改写和规范化，确定业务意图、稳定资源身份、执行者及候选 revision。审批 callback 的合法改写也必须记录其实际覆盖的最终版本或批准的变换约束。
5. 权威准入服务原子检查当前授权、定义版本、证据、预算及冲突，记录 reservation/intent。
6. 发送点重新核对最终绑定、当前政策及其他会变化的条件。对外发送由持久出站安排与目标幂等/对账策略共同约束；出站队列本身不保证外部 exactly-once。
7. 观察适配器保存原始返回和目标读回；可信验证器按固定规则生成候选 CompletionWitness。
8. 接纳验证结论并更新 Supported 与受影响消费者的 Usable，不把某主体拒绝读回自动升级为全局不可用；需要人或评分器验收时，绑定对应版本等待决定。
9. 更新图和工作台投影，解除已证明解决的占位；迟到可信观察仍归属原动作，并可影响当前共享资源判断，但不能覆盖后继尝试的身份；错误/未知效果保留并给出下一项可操作恢复步骤。
10. 执行后记录成本、失败、上下文缺口与验收差异，为改进候选提供材料。

这些步骤是逻辑边界，不要求部署成十个微服务。第一版可在一个进程中实现多个接口，但必须保持各字段由谁产生、谁验证、何时提交的语义。

当前代码连接时有一个先行切片：history 绑定的可信命令入口与正确状态投影。`server/projects.js` 的线程 `accept` 只改变 `phase`，不是 Record 的验收令牌；`checkAction` 是新动作预检查，`dispatch` 才针对既有占位判断；历史 receipt 重送不产生新授权或新的派发许可。首片可保留 kernel，不发送真实外部动作，先验证路由和主体入口确实覆盖所有调用路径。[源码映射独立审查](proof-review/record-mapping-audit/REVIEW.md)

## 8. 三个贯穿场景

### 场景 A：Coding 改动到交付

目标是一个可演示的功能。需求讨论形成契约 v1，代码尝试 A1 绑定提交 s1；测试结果和截图只能证明 s1 上的指定条件。之后用户改要求形成 v2，旧结果仍留在历史，只有与 v2 无关的证据可按明确规则复用。代码合并、构建产物、部署版本和用户验收各有自己的证据，不能因为 A1 的测试通过就让所有后继绿色。

这个场景首先验证工作台、Record、代码影响图和验收绑定。它不要求先有自主记忆服务，也不要求先实现完全通用的长任务引擎。

### 场景 B：远程长期工作与断连

工作契约绑定远端环境代际 e1 和逻辑动作 k。控制连接断开后，远端进程可能继续；新的控制器实例 h2 只能取得恢复权限，不能据此宣称 h1 及其子进程已停止。恢复时先读环境和效果状态，再决定接管、等待、对账或发起新尝试。预算应继续计入可能仍运行的旧任务。

这个场景验证会话/宿主/环境分离、旧发送者占位、目标端证据、在途成本和显式恢复。用户最需要看到的是“仍有哪项工作可能发生作用，下一步怎么确认”，而不是一个笼统的离线图标。

### 场景 C：长期研究与工作方式改进

系统持续跟踪一个已采纳方向，定期形成证据变化与改进提案。新论文先成为来源，经过适用性判断后才成为某个假设的支持；候选方法进入小规模对照，达到约定收益与风险条件后才建议采纳。旧结论被反例推翻时，Record 保留变更理由，图只重算实际受影响的判断，不删全部历史。

这个场景验证材料来源、时点、版本、覆盖义务、最低跟踪投入和变更评价。沿用已有决定：系统可以降低投入；对已采纳方向的彻底暂停由人决定。但预算或权限失效时，系统仍须停止不被允许的新动作，并清楚区分资源等待与主动放弃方向。

## 9. 工作台怎样呈现复杂性

默认视图围绕用户要作的决定组织，不要求用户先理解所有内部版本号。

| 用户问题 | 默认呈现 | 展开后可查 |
| --- | --- | --- |
| 现在做到了哪里 | 当前目标、最近有效进展、下一步 | 任务/尝试/事件版本和原始证据 |
| 为什么停住 | 缺哪个输入、权限、资源或外部结果 | 准入失败条件与恢复选项 |
| 能不能信这个完成 | 已证实部分、当前可用性、待验收项 | 验收规则、产物版本、观察来源 |
| 改需求影响什么 | 直接受影响任务和可能复用证据 | 带类型的依赖路径、AND/OR 支持 |
| 断线后会不会重做 | 已确认效果与仍未知的效果 | 发送者状态、幂等身份、对账证据 |
| 为什么建议换方法 | 预期收益、验证成本、已有对照和不确定项 | 工作流版本、对照记录与失败样本 |

总体状态可以简洁，但点击必须到达支持该状态的证据。用“正在等待确认”“已完成但产物当前不可取”“原完成判断已撤回”等准确文字；不要把所有异常压成红色失败，也不要拿活跃度替代目标进展。

## 10. 实施切片与验收门槛

本轮仅设计切片，不自动执行产品改造。每个切片都应在上个边界可信后继续；期限由真实集成试验再估，不用文档长度推算开发完成时间。

| 切片 | 目标与涉及契约 | 不可破坏的条件 | 关键验收 | 进入下一步的阻断项 |
| --- | --- | --- | --- | --- |
| H01 统一名称与投影 | 将任务、尝试、完成、可用、验收在工作台中区分 | 保留当前历史身份和来源引用 | 给定同一轨迹，UI 与 Record 返回一致且能解释版本 | 当前证据命名仍混淆 |
| H02 持久化权威内核 | 命令接纳、日志与投影原子持久化 | 身份认证、防重放、唯一历史；失败不半写 | 崩溃点注入、重复提交、旧快照恢复均保留一致收据 | 未定义存储事务和身份边界 |
| H03 真实效果适配器 | 对一个具体 GitHub PR 动作做准入、发送与权威读回 | 发送前重新检查；unknown 不自动重放 | 在发送前后、回执前后断开，核实真实目标状态与唯一效果 | 合成证明还没有可信来源 |
| H04 有类型依赖 | 准备/证据/产物关系与有限无环 AND/OR 支持条件 | 撤回不删历史；替代证据可以继续支持；禁止无根循环自支持 | 演示错误完成撤回、结果不可用、部分证据复用和依赖重算 | 仅按可达关系粗暴全失效，或未定义递归支持语义 |
| H05 上下文编译 | 来源版本、水位、必带义务、冲突和 gaps | 权限不因检索扩大；关键约束不静默删除 | 固定资料集中的反例检索、近期纠错优先、预算不足明确返回 | 没有测得遗漏/质量代价 |
| H06 第二宿主/远程恢复 | 验证公共契约与能力声明，绑定 host/environment generation | 不把环境恢复当效果结束；旧发送者保留 | 同一故障轨迹在两个宿主产生兼容判定，缺口可见 | 只能靠宿主私有字段表达核心语义 |
| H07 成本与长期义务 | 在途负担、结算通道、期限和最低复核 | 有限预算不承诺无限活性，等待不伪装进展 | 并发成本越界反例、预算耗尽后结算、不可行义务报警 | 成本上界/截止义务不可测 |
| H08 工作流改进闭环 | 从失败样本生成候选并进行对照 | 固定评估范围；候选不能改自己的硬约束 | 同一任务域的基线/候选比较、失败样本回流及回退判据 | 只有自评或训练集式回归结果 |

本路线使用 H01–H08 编号，不替换现有 Record PR 中“Record S1”的历史名称。

## 11. 最小可展示成果

建议先提供一个可以亲眼核查的示例：一个 Coding 任务在两个尝试之间改了要求，旧证据保留但不再满足新定义；一次外部动作断连后保持 unknown，经权威对账确认后才恢复；最后工作台展示完成证据、当前产物和验收绑定。示例内容用公开的演示仓库和无敏感数据的任务。

围绕这个示例，可以形成几个独立可使用、共同服从同一契约的作品：

1. 项目工作台：面向人的目标、图、证据和验收界面。
2. Record：状态/证据契约和确定性内核，随后增加持久化与上下文编译。
3. 有类型 DAG：依赖表达、影响分析与可视化组件。
4. 远程执行适配器：会话/环境/发送者分离与恢复信息。
5. Harness 行为样例与核查工具：把取消、未知效果、证据撤回、旧验收等反例转为可共享的适配检查。

这些是候选产品边界，不以插件数量作为成果。第五项是否作为独立插件，取决于其他作者能否直接使用；一个清楚的协议与可重复反例集，也可能比额外包装一个插件更有价值。

## 12. 尚未决定

- 首个持久存储和并发范围：单用户单进程、单机多进程还是服务端多用户，应由首个真实场景确定。
- 目标端无法幂等或权威对账时，怎样把“未知、需人决定”呈现得足够实用。
- 验收规则变化、证据过期、主体权限撤回分别使哪些旧决定不再适用。
- 自主记忆的价值是否超过简单来源索引与固定上下文；必须由任务对照回答。
- 图关系达到什么规模才值得引入图数据库；第一版不先选重基础设施。
- 同一公司产品不同接口/版本的语义差异如何被适配能力声明覆盖。
- 工作方式改进采用的评估分布和成本期限；没有共同分布就不报告一个普适收益数字。
