RL1：上界、共享和并发

对同一时刻，把真实占用按物理分配及额外开销分解，若各项均被相应上界覆盖，则对不等式逐项求和即可得到容量界。该推导没有证明上界如何取得，也没有证明内核或宿主遵守上界；原稿已保留这些缺口。若只在准入时观测一次，之后 b、H 或容量变化不再满足前提，不能沿用结论。

RA01 的最小补充建议：“T 覆盖所有同时在途准入/重建/复制操作的合计瞬态；J 为未用交互/收尾预留，实际使用时原子转记到已覆盖分配，或另有实际占用不超过 J 的约束。”两种 J 解释都可用，应选清楚。不要求将 J 永远额外计一次；重复保守占位虽影响利用率，却不会单独推翻上界。

合成例子（数字为假设）：

  • 两任务引用同一 2 单位物理分配，实际总量为 2；按任务各记 2 得 4 是保守重复计数，不能当精确测量或收益。
  • 同内容的两份独立物理分配各占 2，若按 logicalObjectId 合并成 2，则真实为 4。它违反“不同物理分配清单完整”的前提；原稿第 62 行已经明确区分。
  • C=3，两个稳定分配各为 1，两个并发瞬态也各为 1；若把单操作瞬态 1 当全局 T，账为 3，实际峰值为 4。正确 T 至少为 2，或准入协议保证瞬态不重叠。原文的“瞬态不漏项”排除了这个错误，本建议使它更易实现。

本轮枚举三个物理分配的 0≤a≤b≤2、小域 H/T/J/容量，共 23328 个赋值，其中 7803 个满足容量准入，直接实际求和均不超界。这只复核给定上界的算术，不是新的物理内存证明；它也不测调度、尾延迟或共享收益。

RL2：refs 是协议投影，不是使用事实本身

原稿的充分条件包含“全部旧使用已结束/迁移”，所以不能用一个错误计数器把仍活跃的使用者叫成已经结束，再说命题被否定。实际需要证明每个使用都持有有效引用，释放回调只能消费它所对应的那个引用，重复回调不消费别人的引用，资源代际不能混淆。

本轮小状态机使用两个用户、两代资源，Acquire/Retire/Release 原子，真实 users 与 token 集合分开记录。正确方案的 (allocationGeneration, useToken) 释放幂等，只有 retiring 且引用归零才释放；180 状态、304 边内没有“已释放资源仍被使用”等指定不变量违例。未保证每个用户最终结束，也未保证 OS 何时回收内存。

错误变体仅把释放改为“每个 callback 都减少当前 count”，其余保留：656 状态、1908 边。最短 5 步使 count 与有效 token 数不一致；最短 7 步错误释放：

Acquire(A) → Acquire(B) → EndUse(A) → Release(A) → Release(A) → Retire → ReleaseAllocation

此时 B 仍使用资源。该变体满足“新 Acquire 只能 active、Retire 后禁止 Acquire”，但不满足“释放前所有旧使用确已结束”。这准确定位 refs→真实使用的精化义务，不是 RL2 本身错误。枚举也允许旧代 callback 晚到，正确方案按 token 代际无害忽略；不能只靠资源的可复用字符串 ID 扣减当前引用。

见 check_conditions.py、results.json、execution_receipt.json。这是本审查线编写的合成检查，不是另一个作者独立实现的产品验证器；没有运行六类拟议真实场景。
