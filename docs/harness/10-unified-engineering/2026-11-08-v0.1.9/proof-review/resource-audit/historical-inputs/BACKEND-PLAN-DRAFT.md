## 2. 后端怎么做

### 2.1 延续插件内的模块化实现

推荐继续使用现有 JavaScript ESM、Node 内置能力和 DSH 插件服务。`index.js` 负责端点与工具注册，业务逻辑放进 `server/`。将事件归约、状态计算、分组、图和时间线构造做成纯函数；需要读 DSH、Git、文件系统的地方集中到适配层。

| 方案 | 维护与交付成本 | 适合的条件 | 本期判断 |
|---|---|---|---|
| 现有插件＋有界小状态＋独立实时内容目录 | 最接近现有实现；沿用单进程写队列，增加轻量读取与生命周期管理 | 单用户、单宿主拥有数据目录 | 推荐，先测资源基线 |
| 独立后端服务＋数据库 | 增加部署、通信、迁移和宿主身份衔接 | 明确需要跨宿主共享、多人协作或远程访问 | 有此需求后再设计 |
| 修改 DSH／dsh-tui 上游 | 增加升级跟随与回归范围 | 插件能力已证实无法满足关键需求 | 本期沿用交接包的插件边界 |

建议按职责组织为：

- `Store` 管项目事实和串行写入；目标、布局、当前状态属于常驻小状态，历史和已完成消息应有按需读取／归档策略，不能无限扩张常驻对象。
- `Native` 统一读取宿主会话、运行状态与事件，维护增量读取所需的游标。
- `status/overview/map/timeline` 从同一份事实计算视图，避免各端重复解释状态。
- `library/live` 共用路径校验；实时正文与项目索引分开保存。
- HTTP 接口与 TUI 组件调用同一组内部服务，权限检查也在内部服务执行。

现有存储已经使用“写临时文件、rename 替换、串行队列”，应保留并补迁移和失败恢复测试；它没有跨进程锁，也不等于数据库事务或断电持久性保证。[存储实现](../../../server/store.js)

**桌面和 TUI 的宿主关系要先定。** 本期默认每个数据目录只有一个宿主负责写入。如果两端实际启动为独立进程，先用各自的 `dataDir`，并明确不承诺跨宿主同步；如果必须同时看到同一项目状态，就应由一个宿主统一持有存储、另一端通过接口访问。后一种要求需要重新估算，不能让两个 `Store` 实例直接共享同一个 JSON 文件。[目录默认值](../../../index.js)

### 2.2 会话仍由 DSH 管，项目只补必要语义

会话正文、发消息、审批与回答继续使用原生会话组件。项目层只存成员关系、工作阶段、目标、证据、布局和实时内容索引。保留现有 `agent-message` 来源与工作树权限，不把工作线程汇报提升为用户授权。

项目成员当前禁止另起 `workflow/subagent/Team`。因此，项目时间线来自 B01 的线程阶段历史；普通会话的 workflow 时间线是另一条读取路径。地图中的子代理只展示宿主能证实的已有关系，不为做出设计稿效果而放开分派限制。[工具守卫](../../../index.js)

### 2.3 更新由事件驱动，轮询作为兼容方案

调整第一版“默认沿用每 2.5 秒轮询”的建议。优先复用宿主已有事件和插件订阅：一个项目建立一份轻量状态投影，多个视图共享读取；仅相关字段变化时通知订阅者。同进程 TUI 直接订阅内部服务，桌面优先通过宿主现有连接获得失效通知。若安装宿主没有合适推送能力，再使用单一协调器做可见时的轻量版本查询，合并重复请求，空闲退避；`pollMs = 2500` 只作为现有兼容起点，不作为性能结论。

语义事件与绘制分开：审批、错误、完成、用户输入和持久化不能被节流丢弃；文本流可以合并多次更新后绘制，队列必须有界。客户端游标断档时重新取有界快照恢复，不能静默跳过事件。关闭面板只停止正文加工和绘制，后台任务、必要的状态投影与提醒继续工作。

文件变化用宿主通知或按需 watcher 标记失效，读取时核对身份、时间和大小；只在打开内容或已知变更时按需要计算指纹，避免为判定“没变”反复读取全文。Git 查询按仓库去重、合并并限制并发，隐藏资料库不进行周期性 Git 扫描。Node 官方说明 `fs.watch` 存在平台差异，写入也需要串行等待完成，因此通知要有读取校验和失败恢复。[Node 文件监听说明](https://nodejs.org/api/fs.html#caveats)、[Node 文件写入说明](https://nodejs.org/api/fs.html#fspromiseswritefilefile-data-options)

### 2.4 内存与 CPU 是接口和界面共同的设计条件

当前安装的 dsh-TUI 已有共享动画时钟：不可见或传入暂停值时退订，窗口失焦时降频；面板 badge 相同则不再广播。上游架构还说明了可视区域渲染、有界缓存和终端差分输出。新增面板应复用宿主公开的 React／UI kit／时钟，不能另装一套渲染器或为每张卡建立定时器。具体能力以固定安装版本验证，GitHub 主干文档不代表本机已具备全部新能力。本机动画实现（原文引用，未随公开文档附带）、本机 badge 去重（原文引用，未随公开文档附带）、[上游架构说明](https://github.com/ccch1mneyyy/dsh-TUI/blob/main/docs/architecture.en.md)

| 设计对象 | 从第一版执行的规则 | 保留的体验与功能 |
|---|---|---|
| 项目列表与卡片 | 一份投影、按项目订阅；返回摘要字段，避免多个组件各拉一次所有项目；未变字段保持引用稳定 | 分组、计数、状态和提醒一致，各入口仍可及时更新 |
| 会话正文 | 摘要、尾部、分页正文分开；冷会话不为了卡片而激活 Agent；缓存只保留近期及可见窗口 | 全历史仍由宿主管理，需要时加载，不删用户历史 |
| 缩小与隐藏 | 缩小为摘要卡；重正文树按需释放。先验证草稿、滚动锚点可由宿主或小状态恢复；取消在途读取、解除订阅 | 会话任务继续，重新展开能恢复输入和位置 |
| 长列表、目录、地图 | 按可见窗口挂载；目录分层读取；图只在结构改变时重算布局，状态变化只更新节点；TUI 优先树形／列表表现 | 保留完整查询、展开与导航，不用后台重排换取表面流畅 |
| 流式文本与日志 | 输入增量归约，绘制批量合并；Markdown 只重新处理受影响块；正文和测量缓存按字节及条目双重限制 | 正文最终完整、滚动顺畅，工具和审批事件即时可达 |
| 动效与视觉 | 保留统一颜色、层级、留白和状态符号；只给可见变化运行短转场，复用宿主时钟；静止时不新增持续重绘 | 美观通过稳定布局和必要反馈实现，不以全面关闭动效代替优化 |
| 图表、图片、富文本 | 打开时再加载、解码和布局；显示摘要／缩略图，缓存可释放；数据与渲染格式分开 | 可以查看完整成果，未打开时不预先消耗解码内存 |
| 存储与队列 | 原文、历史和已完成内容保留在持久层；常驻索引有界；写入只针对有意义的状态变更，不把每个 token／动画帧写入项目 JSON | 重启可恢复、证据可追溯；归档已发送消息时保留防重放凭据 |
| 插件生命周期 | 订阅、计时器、watcher、在途任务都归一个 owner，卸载可释放；禁止卸载后回调继续更新 | 热重载与面板反复开关不积累资源，也不影响正在执行的宿主任务 |

已发现的开销候选有直接代码依据：`useProjects` 的每次挂载会建立独立轮询，多处组件调用该 hook；`Projects.list()` 会克隆完整状态；`Projects.read()` 先对全部事件做 filter/map，再从结果截取尾部。建议优先解决这些重复工作，再根据 profile 决定是否需要进一步拆分存储。**这属于静态识别的候选热点，尚未测得它们各自占用多少内存或 CPU。** [轮询入口](../../../client/app.js)、[项目列表](../../../server/projects.js)、[全状态复制](../../../server/store.js)、[消息尾部读取](../../../server/projects.js)

缓存不是越大越快：正文、解析结果、宽度测量、图数据分别登记容量与释放条件，并有总预算；只限制磁盘项目数不能保证内存有界。保留现有低频状态写入队列，先减少读取侧的全量复制；若长历史／outbox 使全量 JSON 写入越过预算，再以测量结果选择按项目分片或独立追加日志。不能直接删历史或去重记录来换取低占用。

### 2.5 第一个里程碑就建立资源验收

先用固定宿主版本、相同终端、相同窗口大小和主题测三组：A 为原版 TUI，B 为加载工作台但面板关闭，C 为工作台正常使用。使用独立夹具与可重复事件回放，分别测冷启动和预热后的稳定阶段；真实模型另验功能，不把网络或推理波动混入 UI 性能对比。每组重复采样并报告中位数、尾部与峰值。

| 度量 | 要记录的内容 | 前置判据 |
|---|---|---|
| 总体与增量内存 | 宿主 RSS／峰值、JS heap、external／Buffer；同时观察终端模拟器，桌面则另看 renderer | 同时报告应用总量与 B−A、C−A 增量；固定负载反复开关后资源应回到稳定平台，不能随开关次数持续增长 |
| CPU 与唤醒 | 空闲、流式、滚动、缩放的 CPU 时间和定时唤醒；统一以单逻辑核 100% 计算 | 无数据变化且无新增动效时，新增面板的重绘为 0；关闭后的正文扫描、周期 Git 查询和动画 tick 为 0 |
| 交互与绘制 | 按键至可见反馈的 p95/p99、帧耗时、event-loop delay、实际写终端的字节量 | 输入和审批不被日志／图计算阻塞；必要重绘范围随可见窗口而不是完整历史增长 |
| 内部资源 | 队列字节数、缓存占用、订阅数、watcher、文件句柄、Git 子进程数 | 容量和并发有明确上限；插件卸载／重载后不残留注册资源 |

常用负载沿用现有 64 条线程上限、3 条并发任务及桌面最多 3 个展开会话；TUI 按实际活动面板测。再用分级长历史、大文件、持续流式、反复开关、resize 和重连做压力场景。固定负载才能判断是否泄漏；RSS 不立即下降不能单独判泄漏，要结合 heap、仍被持有的对象和句柄判断。

**绝对 MB、CPU 百分比、输入延迟上限在 D2 根据原版基线和目标负载确定，并在实现时登记到超参数／基准配置。** 当前只读确认本机为 16 GiB、8 逻辑核，这能作为首台验收机器，不能替代较低配置设备的验证。没有基线前不宣称“只占几十 MB”或给出节省比例；尚未建立预算的卡不能被标成性能通过。

测量本身也要轻量：普通采样优先 RSS 与 CPU 时间，详细 heap／分配追踪仅在基准或诊断时启用。Node 文档说明完整 `memoryUsage()` 可能有遍历开销，RSS 专用接口更轻；事件循环延迟只反映一部分阻塞，不能替代真实按键至屏幕反馈测量。只使用实际 Node 版本支持的指标。[Node 内存与 CPU 指标](https://nodejs.org/docs/latest-v24.x/api/process.html#processmemoryusage)、[Node 事件循环测量](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html#perf_hooksmonitoreventloopdelayoptions)

## 3. 开工前先补齐的契约

这些是对现有任务包的修订建议，尚未写入 `CONTRACT.md`。建议在前两个推进日与资源基线一起定稿，给 Claude 一份固定的数据样例、错误响应及加载／卸载约定，再开始业务卡。

| 优先级／关联卡 | 当前缺口 | 建议落地规则 |
|---|---|---|
| 必须先定：所有读接口与 B11 | 缺少查询成本、缓存与订阅生命周期约定；TUI 的可行性验证放得太后 | 区分摘要／正文／历史分页，定义增量失效、请求去重、隐藏时退订和资源预算；先完成 TUI 最小面板挂载与释放验证。变更卡片允许文件清单，使性能夹具与测量代码有明确归属 |
| 必须先定：B01–B03、B09、B10 | B01 只在 `store.change` 后加版本；审批、提问、运行状态、交付文件和磁盘文件变化未必调用它 | 明确每个读接口的版本作用域及失效来源。项目视图版本覆盖会话投影变化；布局用自己的 revision 做并发检查，实时单项用自己的内容版本。重启后必须能使旧缓存失效，不能误回 `notModified` |
| 必须先定：通用响应 | 通用条款要求读接口带 revision，但多个具体响应未列；部分写接口也缺完整入参／结果 | 在契约中逐一列出请求、成功、业务错误、未变化、冲突和截断响应。B12 的 schema 与样例校验从第一天建立，贯穿每张卡 |
| 必须先定：B03 | 已解决组默认截断，完成判据却写“四组线程数相加等于总数”；“显示更多”没有游标 | 总量以 `counts` 计算，页面条数单独计算；补稳定排序的分页方式，推荐游标。测试超过默认数量后的第二页、空页和并列时间 |
| 必须先定：B02 | 待审批、待回答、计划待审之间的顺序，以及停止／重连后遗留事件的处理不完整 | 优先复用宿主的待交互语义，明确多种等待同时存在时的顺序；按请求 ID 配对结束，区分取消、超时后仍可回答和宿主已中断，避免一条旧事件让卡片永久等待 |

## 4. 交付顺序与时间计划

这里的“有效推进日”指当天能完成一轮实现、验证、审阅反馈或必要的联调。它不是模型持续运行一天，也不要求用户全天编码。第二版含资源设计和测量准备，按每周五个推进日计算，完整任务包约四到五周；如果每周只能推进三天，则约六到八周。暂不绑定固定上线日期，D2 后重新校准。

| 时间 | 后端工作与任务卡 | Claude 需要同步提供的前端结果 | 阶段验收与用户投入 |
|---|---|---|---|

| D6–D8 | B07 会话尾部和分支、B10 布局、B05 项目目标 | 卡片／分屏／目标页接线，摘要与重正文分层加载 | 第一版日常可用；顺利时 D6 试用，完整阶段目标取 D8。关闭正文仍保留任务与草稿，缓存和订阅可释放 |

**最早的日常可用版本依赖前端接线。** D8 后端完成而 Claude 尚处于设计阶段时，只能交付接口和测试证据，整套界面的可用日期随前端接线顺延。D18 同样是完整任务包的条件计划，不是全部设计画板都已产品化的承诺。TUI 首轮挂载和资源验证已前移，后段是完整功能收口。

| 真实宿主 | 用户在独立验收项目与小型 Git 夹具上操作；记录桌面／TUI 版本、输入、结果与证据 | 确认安装版本、组件挂载、权限、焦点和实际操作可用 |

## 8. 开源候选与优先研究方向

按设计范围已确定，本轮使用 **GPT-6.1 Terra** 完成检索初筛，覆盖 **34 个代表项目**；主会话完成汇总和重点来源抽查。清单同时覆盖整体架构和各小方向，完整仓库链接、许可证、适配成本与核对深度见[开源选型讨论稿](<OPEN-SOURCE-RESEARCH-DRAFT.md>)。本轮的“研究价值”不等于已经验证可接入或资源更省。

|---|---|---|
| 现有基础 | 优先读 DSH、Cordis、dsh-TUI | 核对状态事实来源、扩展 API 和释放机制，继续复用宿主能力 |
