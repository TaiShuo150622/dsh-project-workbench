## 用户行为

项目卡片提供“管理项目”入口，在新总会话尚未发送模型消息时也能打开。用户可编辑整体目标、逐行维护验收条件、上下移动工作线程并保存；线程总览也显示同一编辑面板。

顺序只影响依赖已满足、尚未启动的线程。正在运行的任务不被停止或重新派发。验收条件是用于判断结果的文本，本线不自动把项目或线程标记完成。

保存冲突会显示明确错误并保留草稿；轮询不会覆盖未保存编辑。用户可主动载入最新保存内容。新目标本身不授予新的操作权限，也不替代已有任务与审批范围。

## 持久化与接口

状态保存在项目的 `coordination` 字段：

```text
{ revision: 非负整数, goal: 字符串, criteria: 字符串数组, order: 本项目线程 ID 数组 }
```

| POST 接口 | 入参 | 成功返回 |
| --- | --- | --- |
| `coordination-read` | `projectId` | 当前协调状态 |
| `coordination-update` | `projectId, expectedRevision, goal, criteria, order` | `{conflict:false, coordination}` |

接口继续使用工作台原有 RPC 信封。版本比较、输入验证和写入均在现有 `Store.change` 串行事务中完成。旧版本提交返回 `{conflict:true, coordination:当前状态}`，不会覆盖目标。其他校验失败走原有 `{ok:false,error:{message}}` 信封。

验收条目必须是非空文本；目标与验收文本合计使用现有 `maxText` 限制。顺序拒绝重复、未知及跨项目线程 ID。未显式列出的新线程保留在顺序末尾，防止并发新增线程被旧编辑页面遗漏。协调版本只表示目标、验收和显式顺序保存的版本，不代表整个项目所有状态的版本。

缺少协调字段的旧项目读为版本零、空目标与验收、原线程顺序；读取不修改原记录，首次保存新增字段。已存在但格式不支持的协调字段会报错，不静默重置。

## 线程与模型上下文

线程从排队进入正式运行时，将本轮 `adoptedCoordination={revision,goal,criteria}` 与任务消息在同一事务中写入。运行中的线程保留该快照；下一次自然继续才采用当时的新版本。上下文明确区分本轮采用版本与当前项目版本。

模型通过现有 `project_threads` 和项目上下文读取状态；没有新增修改目标的模型工具。界面维护 API 沿用宿主的访问边界。依赖就绪仍沿用现有 `review` 或 `completed` 规则；本线未修改依赖的验收语义。

实现文件为 [服务](../../../server/coordination.js)、[界面片段](../../../client/coordination.js)，接入现有项目服务、RPC、项目页、线程总览和构建脚本。
