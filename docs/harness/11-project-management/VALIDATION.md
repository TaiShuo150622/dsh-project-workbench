## 审查与组合修复

审查等级为同模型、不同上下文。恢复线审查发现后续队列被新任务覆盖、创建失败身份丢失、未知 worker 阻挡总会话汇报重试，新增回归先复现失败，再修复通过；观察期间发生暂停也会在正式启动前重新检查。接续线审查发现跨项目迟到响应串位和保存期间草稿被清除，补项目 key 与输入保护并验证。

组合验证还发现：新接续摘要会把最新目标泄漏给仍采用旧目标快照的工作线程。已在 B 线修复为只有协调会话和历史协调会话注入当前接续摘要，工作线程保留本轮采用版本，并加入回归。共享测试桩补齐三条接口契约后，组合验证通过。

真实宿主暴露旧 `sessionController.inspect` 被移除；兼容层改用 `sessionPersistence.open(id, 'read')`，读完释放 handle，保留旧 API 适配。检查不调用 `resolveAgent`，避免读取状态意外激活冷会话。

宿主客户端模块注册表曾保留旧构建，使用隔离环境的一次性维护脚本刷新注册表；主进程及工作会话未重启，维护入口已停用。

## 真实运行结果

详见 [真实组合试验](LIVE_TRIAL.md)。I1 用原句让真实模型建立两条只读研究线程，两份汇报回到协调会话，约 60.4 秒进入稳定待验收状态。I2 在空闲后创建新协调会话并明确开始，约 18.2 秒返回基于有效决定、接续包和原线程的答复。两次均通过真实宿主接口发起，不是模型桩或回放。

接手、状态核对、重新认证连接后，两个工作线程的 ID、会话 ID 和 generation 均未变化；仍为两条线程、generation 1、`review`，无重复工作任务。三份合成输入文件 SHA-256 前后相同，待投递汇报为 0。`review` 表示等待人工验收，不能记作整体成果已验收。

内容复核发现，新协调会话正确引用了替代后的有效决定，并保留尚未交付验收说明的事实，但对“两条汇报没有冲突”的表述偏乐观：一条严格区分原文约束，另一条提出去空白、name 非空等建议，两者不能自动合并成规范。本轮验证的是管理状态和接续链路；内容的一致性与最终验收仍需人工核对。
