# 实时讨论工作台的开源参考与公共核心

> 公开整理版 · 整理日期：2026-11-06 · 源版本：未标版本；2026-10-28。
> 保留个人通用研究、方法和公开来源；已省略公司案例、项目专属实现、个人身份与会话材料。
> 本次仅整理文本，未重新运行原实验、复测宿主兼容性或更新外部资料；历史结论仍受原研究范围限制。


调研日期：2026-10-28。本文依据官方仓库、文档和许可证整理；未安装、运行或测试候选项目。文中的架构方案属于设计建议，尚未形成实现规格。

**建议建立自己的公共核心，采用可替换的语音组件，并借鉴现成产品的数据模型和处理流程。** 本轮查到的项目分别覆盖实时转写、会议记录、资料检索、层级引用和图形显示，但尚未找到证据证明某一个项目完整满足“实时理解讨论、持续纠正、选择可视化、提示缺口、核验证据、多用户权限”这条链路。第一轮值得重点研究的是 Anarlog 的会话与提供方接口、FunASR／sherpa-onnx 的语音路径、Omi 的实时扩展，以及 Trilium 和 Open Notebook 的资料引用方式。以下比较说明它们各自能提供什么依据，避免把完整产品的宣传范围直接当作可复用模块的能力。

本文的产品假设是：单人梳理、两人讨论和多人会议共用后端；语音为主要输入，图片补充背景；前端可以后做；资料按项目、人物和多层目录组织；“人”同时包括登录账号和联系人／参与者；云端与完全本地处理均应提供可选配置。三种场景的主要差异放在行为策略里：单人模式保留探索分支，双人模式强调共识和分歧，会议模式强调议题、决定和行动项。

**开源参考应区分直接接入的组件与学习设计的完整产品。** 下表中的“适合”是研究优先级，不代表已经验证兼容性。

**资料管理需要把“谁能看”“资料放哪”“资料与谁有关”分开。** 推荐采用下列概念模型。它借鉴了 Trilium 的多入口引用和 Open Notebook 的共享来源关系，具体组合是本项目的设计建议。

| 层次 | 对象与职责 |
|---|---|
| 账号与权限 | User 表示登录账号；Workspace 容纳个人或共享资料；Membership 与资源权限描述访问范围。 |
| 人物与项目 | Person 表示联系人或参与者，可以没有账号；Project 组织跨会话的目标与知识。一个账号可关联人物档案。 |
| 录音身份 | SpeakerLabel 仅表示本次录音中区分出的声源，通过确认或可信音轨信息关联人物。 |
| 多层目录 | Folder 保存父子层级；目录入口引用稳定内容 ID，支持同一资料出现在多个位置。 |
| 内容与依据 | Asset 保存录音、图片等资产；Session 和讨论对象记录内容、关系、来源与版本。来源可定位到音频区间、转写片段或图片区域。 |

例如，一场对话可同时出现在“项目 A／需求讨论”和“张三／沟通记录”中，两个入口指向同一份内容。移动目录、移除入口和删除资产是不同操作；人物或项目关联也不改变资产身份。账号权限贯穿这些入口、搜索、跨会话检索和派生摘要。关联某个人、把资料加入共享项目，都不自动授予访问权。跨工作区引用的具体规则仍需明确。

这个区分也有产品依据：Anarlog 分别维护联系人及会话关系，并允许把转写中的说话人标签手动关联到参与者；这为“匿名发言人”和“真实人物”之间的确认步骤提供了参考。[联系人文档](https://docs.anarlog.so/contacts)、[转写编辑文档](https://docs.anarlog.so/notes)

**本地与云端模式应覆盖完整处理链。** 建议给用户两套预设，底层分别配置转写、语义理解、图片解析、嵌入与索引。资料存储位置、同步策略和外部联网查证另行设置：本地推理可以使用本地资料库；启用同步则按明确配置执行；完全离线时，证据来自已导入或下载的材料。本地某个阶段不可用，应展示该能力不可用，不能静默改用云端。Anarlog 将本地转写与本地摘要模型分开准备，且区分实时与录音后处理，这说明需要逐阶段核实离线能力。[离线文档](https://docs.anarlog.so/offline)

公共接口保持一致：语音适配器输出片段、时间范围、音轨、说话人标签、文本版本和临时／稳定状态；模型适配器接收权限范围内的上下文，返回带来源的更新建议。本地或云端配置改变执行位置，业务对象和修正语义保持稳定。第一轮可以比较 FunASR 与 sherpa-onnx 的中文路径，并学习 WhisperLiveKit 的整合方式；人数、抢话和重叠转写需要独立验证，不能从“支持分人”推导完整会议效果。

**需要自己建设的部分，是让讨论状态正确地持续变化。** 建议主流程为“录音／图片 → 带来源的输入记录 → 讨论状态更新 → 可视化计划、问题、证据与行动建议”。讨论状态保存目标、观点、假设、方案、分歧、决定和任务，区分参与者陈述、明确决定、AI 推测及待确认内容。后续改口会替代相关旧状态，并同步更新图表、提醒和任务，同时保留依据。

可视化计划描述适合的视图、元素、关系、缺失字段及其来源，前端负责布局和交互。语义状态与布局状态分别保存，便于后续保留用户固定的位置。日期或工期没有依据时，先输出待定任务和依赖；Mermaid 的甘特默认行为不能充当真实排期依据。[甘特语法](https://mermaid.js.org/syntax/gantt.html)

调度也由公共核心负责：快速整理持续处理新信息，较慢的检索独立运行；证据回来时核对相关问题是否仍有效。相同问题去重，已回答的问题收起；截图与发言的指代不明确时留下待确认关系。资料访问条件随检索及派生内容保留，避免模型在总结中暴露请求者无权查看的来源。

下一步适合先确定这些对象、接口和状态变化规则，再在讨论充分后做小范围验证。即使没有正式前端，也可以按真实时间回放单人、双人、多人录音，查看结构化结果是否正确随改口更新，是否保留分歧，能否追溯来源，以及断线后能否延续会话。语音候选用同一组中文材料比较转写、归属、修正频率和资源消耗；本地配置另做断网验证。现阶段不据文档承诺准确率、延迟或硬件需求。

接下来最有价值的设计问题是：多层管理是否还包括“项目／子项目”和“公司／联系人”，还是层级仅发生在目录；个人与团队空间之间怎样共享资料；目录默认权限如何继承；移除入口和删除原件怎样向用户说明。这些答案会收敛公共核心，而前端形态可以继续后置。
